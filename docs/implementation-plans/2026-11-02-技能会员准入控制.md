# 技能会员准入控制实现方案

> 日期：2026-11-02（Asia/Shanghai）
> 状态：已实现并完成验证
> 需求确认：已澄清

## 1. 目标与背景

- **要解决的问题：** 用户可以把技能添加到“我的技能”，但当前点击“使用”没有会员校验；会员概览接口从数据库读取，不能满足每次使用时通过 Redis 核对的要求。
- **功能目标：** 让已添加技能继续对所有用户开放；使用技能前由前端请求会员准入状态，并由后端实际执行接口再次校验；会员状态以数据库期限为准，Redis 缓存用于快速查询。
- **预期最终效果：** 会员点击“使用”后进入技能；非会员看到可关闭的提示，并可跳转到现有会员中心 `/membership` 充值。直接调用实际执行 API 的非会员也会被后端拒绝。

## 2. 已确认需求

- **使用者 / 调用方：** 已登录用户，包括访客；访客不具备会员资格。
- **触发方式：** 在“我的技能”页或技能市场点击已添加技能的“使用”按钮；以及调用技能对应的后端执行 API。
- **输入：** 当前登录用户身份，不接受客户端传入用户 ID 或会员状态。
- **输出：** 会员返回允许使用；非会员收到前端提示或后端 `403`；会员服务/Redis 不可用时不启动技能并返回服务不可用错误。
- **主流程：**
  1. 点击“使用”时，前端调用当前用户会员准入接口。
  2. 后端每次从 Redis 查询用户会员缓存；缓存未命中时按服务端 UTC 时间查询现有会员期限，并回填缓存。
  3. 会员继续执行现有技能跳转；非会员可选择关闭提示，或进入 `/membership` 选择套餐。
  4. 执行技能的后端接口在调用业务逻辑前重复执行同一准入校验，防止跳过前端。
  5. 支付 Webhook 成功提交会员期限后删除该用户的准入缓存，避免新会员继续命中旧的非会员缓存。
- **业务规则与边界：**
  - 会员有效期采用 `[starts_at, expires_at)`；统一使用服务端 UTC 时间判断。
  - 添加、移除技能和查看技能市场不要求会员。
  - 新建/执行技能要求当前会员有效。已保存数据仍可查看和管理。
  - 已创建的周期提醒在会员到期后继续执行；非会员仍可查看、暂停或取消已有提醒，但不能创建、修改或恢复提醒。
  - 只读会话、训练结果、简历及图片结果访问不因会员到期而关闭；消息发送、训练开始/提交、AI 技能调用等执行动作受会员保护。
- **异常行为：** Redis 或缓存未命中后的数据库查询不可用时，拒绝执行并返回 `503`；非会员执行 API 返回稳定 `403`。缓存命中后不会访问数据库。
- **权限与数据范围：** Redis Key 按服务端认证得到的 `user.id` 隔离；查询和缓存只包含该用户的会员资格，不公开其他会员信息。
- **约束：** 复用现有 Redis 客户端、会员期限表、会员错误处理器、技能跳转、会员中心路由和确认对话框；不增加数据库表、字段或第三方依赖。

## 3. 范围

- **本次包含：** Redis 会员准入缓存、准入查询 API、前端使用前检查与双选项提示、技能执行 API 的服务端权限保护、支付成功后的缓存失效、API 文档和对应测试。
- **本次不包含：** 会员套餐/支付流程改造、已添加技能限制、历史数据删除或隐藏、会员过期时取消现有周期提醒、全局导航改版。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| `membership/access_service.py`（拟新增） | 按当前用户核验有效期限；缓存缺失时查询 Repository；提供统一的“需要会员”校验 | 会员业务层依赖会员 Repository 和会员缓存适配器；不依赖具体技能模块 |
| `membership/access_cache.py`（拟新增） | 封装会员准入 Redis Key 的读取、写入和失效 | 只通过现有 Redis 客户端工作；不承担套餐或期限业务判断 |
| `membership/dependencies.py` | 构造准入服务并提供 API 依赖 `require_member_access` | 技能模块通过依赖注入使用会员准入，不在 Router 中写业务判断 |
| `membership/repository.py` | 查询当前有效期限和下一期限状态边界 | 只包含 SQLAlchemy 查询；复用已有 `memberships` 表 |
| `membership/service.py` | 支付确认后提交期限并清理用户会员缓存 | 在数据库提交成功后失效缓存；缓存失效失败走可重试的服务错误，重复 Webhook 可幂等重试 |
| 技能业务 Router | 对创建/运行等执行入口挂载统一准入依赖 | Router 仅声明依赖；会员判断留在会员服务 |
| `MySkillsPage`、`SkillMarketPage` | 使用按钮前调用共享会员准入检查；会员继续启动，非会员显示选择对话框 | 复用 `ensureSkillMembership`、会员 API、`useToast().confirm` 和现有 `/membership` 路径 |

### 关键流程

```text
点击“使用”
  -> GET /api/v1/users/me/membership/access
  -> MembershipAccessService
      -> Redis GET orionai:membership:access:{user_id}
      -> 命中：按缓存值返回
      -> 未命中：MembershipRepository 查询当前/下一有效期 -> Redis SET 带 TTL
  -> 会员：继续现有 skillUsage 跳转
  -> 非会员：显示“关闭 / 去充值” -> /membership

实际执行 API
  -> 当前认证用户依赖
  -> require_member_access
  -> Redis 准入检查（未命中时读数据库并回填）
  -> 原有技能 Service / Agent Runtime

Stripe 已验证支付事件
  -> 现有会员期限数据库事务提交
  -> DEL orionai:membership:access:{user_id}
```

数据库是会员状态的权威来源，Redis 只存短期准入结果。每次前端使用点击和每个受保护的执行请求都读取 Redis；缓存未命中才访问数据库。缓存 TTL 不跨过当前会员到期或未来期限开始边界；支付成功后主动删除缓存。Redis 不可用时 fail closed，返回 `503`，避免无法确认资格时放行。

缓存内容仅保存会员布尔结果及必要的有效边界；Key 使用固定前缀和用户 ID。正向缓存最长 5 分钟且不晚于期限到期；负向缓存最长 30 秒且不晚于下一期限开始。TTL 是会员模块常量，不新增环境变量。访客始终返回非会员，不读取其他用户缓存。

## 9. 接口与数据库变更审查

### 接口影响

| 接口（方法 + 路径 / 事件） | 操作 | 当前定义位置 | 变更前后契约 | 复用判断与变更理由 | 兼容性 / 调用方影响 |
|---|---|---|---|---|---|
| `GET /api/v1/users/me/membership/access` | 新增 | `membership/router.py` 的 `users_router` | Cookie 身份；返回 `{"is_member": true/false}`；Redis/数据库不可用返回 `503` | 现有 `/me/membership` 返回完整期限且走 DB，无法实现每次 Redis 查询，故新增最小准入响应 | 新增接口；前端使用按钮调用；访客返回 `false` |
| `POST /api/conversations` | 修改权限 | `conversations/router.py` | 请求/成功响应不变；非会员新增 `403` | 创建会话是启动技能的一部分 | 会员及历史读取兼容；非会员不能新建 Agent 会话 |

## 10. 分步实施计划

### 步骤 1：建立 Redis 会员准入服务

- **目的：** 用已有会员期限计算统一的当前资格，并确保 Redis 优先读取。
- **涉及文件：** `membership/access_service.py`（新增）、`membership/access_cache.py`（新增）、`membership/constants.py`、`membership/errors.py`、`membership/repository.py`、`membership/schemas.py`、`membership/dependencies.py`。
- **实施内容：** 实现用户维度 Key、缓存命中/未命中和 DB 回填；校验期限起止边界；TTL 不跨过期限变化边界；增加稳定 `403` 准入异常；Redis 或 DB 故障转为 `503`。
- **前置依赖：** 无。
- **验收标准：**
  - [x] 每次准入检查先执行 Redis `GET`；缓存命中不查询数据库。
  - [x] 缓存未命中按 UTC 查当前会员期限，回填 Redis；有效期限包含开始时刻、不包含到期时刻。
  - [x] 缓存 TTL 不跨越当前到期或下一期限开始时刻；用户 Key 互相隔离。

- **验证方式：** 新增的会员准入单元测试使用 Fake Redis、固定时钟和 SQLite Repository。

## 12. 风险、假设与运行考虑

- **非阻塞假设：** 会员期限写入/更新只由当前 Stripe Webhook 成功入账流程触发；该流程负责使缓存失效。若未来添加后台人工改期，也必须调用同一失效方法。
- **主要风险及应对：**
  - Redis 不可用会暂时阻断会员功能；选择 fail closed，保证资格无法确认时不放行。
  - 缓存负值可能遮住刚开始的排期会员；通过支付成功失效及 TTL 截断到下一期限开始时间避免陈旧状态。
  - 用户可能在前端准入检查后、真正执行前刚好到期；后端再次检查可阻止该竞态。
  - 周期提醒到期后仍继续发送是已确认行为；用户仍能暂停/取消，后端调度器不因会员状态改动。
- **安全 / 隐私 / 性能 / 可观测性：** 仅用认证用户 ID 构造缓存 Key；客户端不能传会员状态；准入接口只返回布尔值；不记录用户数据或缓存内容；命中 Redis 后不访问会员数据库。
- **发布、迁移或回滚：** 无数据库迁移和环境变量变更。代码回滚后 Redis Key 会自然过期；可用统一 `orionai:membership:access:*` 前缀批量清理，但不需要清理数据库状态。
