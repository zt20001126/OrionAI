# 数字人点击交互实现方案

> 日期：2026-11-05（Asia/Shanghai）  
> 状态：待审阅  
> 需求确认：已具备实现条件；模型细节已从仓库内的 VRM 文件核实

## 1. 目标与背景

- **要解决的问题：**「我的数字人」页面已有全身 VRM、鼠标跟随和待机/对话动作，但用户点击数字人时没有明确回应。
- **功能目标：**仅在数字人助手页面启用身体单击挥手、头部单击歪头、数字人双击开心回应。
- **预期最终效果：**用户在正常页面比例下能够清楚看到三个动作；每次只播放一个动作，动作结束后由现有待机/状态动画平滑接管。

## 2. 已确认需求

- **使用者 / 调用方：**数字人助手页面用户；未来数字人对话事件可复用同一个 `playGesture("wave" | "headTilt" | "happy")` 动作入口。
- **触发方式：**在模型有效网格上单击身体或头部；在短判定窗口内对模型有效部位双击。
- **输出：**身体单击播放约 2 秒挥手（抬手、约 3 次左右摆动、放下）；头部单击播放约 1.6–2 秒、约 20°–25°的颈头协同歪头；双击播放约 2 秒开心表情、两次点头及轻微身体/手臂配合。
- **业务规则与边界：**背景点击不触发；双击只播放开心动作；动作互斥；无效骨骼或表情时跳过该通道并保留其余动作；鼠标跟随在歪头期间让位，恢复时平滑接管。
- **约束：**复用现有 Canvas 与 `useFrame`；不新增 RAF、模型加载、依赖、后端接口或数据库；不改 VRM 文件、聊天 UI、背景或全身取景；首页行为保持不变。

## 3. 范围

- **本次包含：**公共数字人组件的默认关闭开关、页面专用启用、Canvas 范围 Raycaster 命中判断、点击单双击判定、统一手势动画混合、模型表情支持及对应验证。
- **本次不包含：**AI 对话协议或消息服务改造、VRM 资源修改、页面视觉重做、全局导航变更。

## 4. 需求澄清记录

需求和代码库信息已足够形成方案。动作方向、点击时间窗和手臂角度作为内部实现参数，并在真实模型与正常页面缩放下按验收标准校准，不需要改变用户可见的需求。

**VRM 核查结果：**`frontend/public/models/orion.vrm` 是 VRM 0.0 文件。其 humanoid 映射包含 `rightShoulder`、`rightUpperArm`、`rightLowerArm`、`rightHand`、颈部、头部、胸部、上胸、脊柱以及手指骨骼；肩臂骨链在模型节点中沿局部 X 轴延伸，可通过局部 Z 轴抬臂，再由肘/腕配合做可见摆动。模型包含 `Joy` 与 `Fun` blend shape；已安装的 `@pixiv/three-vrm` 将 VRM 0.0 的 `joy` 映射到 `happy`、`fun` 映射到 `relaxed`，因此优先使用 `Happy`，缺失时使用 `Relaxed`。

动画现状中，姿势通过骨骼基准 Quaternion 和 Euler 目标生成；鼠标 pitch/yaw 只在 idle 状态参与头部目标。助手宿主当前使用包含全身的 `home` 取景，因此有空间观察举手到头部附近的动作，无须更改全身比例或镜头。

**工作区注意：**当前已有 `DigitalHumanPage.tsx`、`DigitalHumanComposer.tsx`、`digitalHuman.css` 和 `i18n/messages.ts` 的未提交改动。本方案不要求修改这些文件；实现时保留现有改动。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| `DigitalHumanAvatarHost` | 为数字人助手页传入 `enableClickInteraction={true}` | 页面宿主配置展示能力，不影响首页 |
| `DigitalHumanAvatar3D` / `VrmAvatarScene` | 将开关传至场景，并把动画 Hook 返回的 `playGesture` 提供给点击交互 | 继续负责渲染，不承载聊天或服务端逻辑 |
| **新增** `hooks/useVrmAvatarClickInteraction.ts` | 只在 Canvas DOM 元素上注册/清理 click 监听；Raycaster 判定是否命中 VRM 网格、头部或身体；延迟单击并合并双击 | 依赖 Three.js 场景/相机/VRM 与动画 Hook 暴露的动作入口；不创建渲染循环 |
| `useVrmAvatarAnimation` | 维护单个动作状态和时间线；由现有 `useFrame` 计算融合目标、Quaternion slerp、表情权重与恢复 | 唯一写入动画骨骼/表情的模块；点击和未来事件复用 `playGesture` |

### 关键流程

```text
数字人助手页
  -> DigitalHumanAvatarHost（启用交互）
  -> Avatar3D -> VrmAvatarScene
  -> Canvas 点击 -> Raycaster 命中模型与区域
  -> 单击延迟判定 / 双击合并
  -> playGesture(kind)
  -> useVrmAvatarAnimation 的现有 useFrame 混合骨骼与表情
```

Raycaster 只监听 Canvas 自身，聊天 DOM 和背景不会进入该交互。命中点高度相对 VRM 颈部/头部骨骼的世界坐标判定头部区域，其余模型网格归为身体。单击延迟约 250–300ms；两个有效模型命中落入判定窗口时取消待触发单击并只播放 `happy`。有效网格被 Raycaster 命中作为前置条件，避免 Canvas 空白处触发动作。

手势作为同一动画系统内的有界时间线：挥手约 0.4s 举臂、1.2s 约 3 个摆动周期、0.4s 放下；歪头将总侧倾分配给颈部和头部，动作期间让点击姿势接管 head/neck 并淡出鼠标跟随；开心动作约 2s 驱动 `Happy`/`Relaxed`、两个点头、躯干左右摆动和双臂轻抬。Ease-in/out 由平滑时间包络实现；各目标经安全角度夹取后转换为相对基准姿态的 Quaternion，并在每帧用 slerp 融合。动作期间相关 idle/status 通道淡出，口型与眨眼仍按现有状态更新；恢复段淡入环境动作。

### 接口影响

| 接口（方法 + 路径 / 事件） | 操作 | 当前定义位置 | 变更前后契约 | 复用判断与变更理由 | 兼容性 / 调用方影响 |

### 数据库影响

### 最小变更结论

- **可复用的现有接口 / 数据结构：**现有 VRM humanoid 归一化骨骼、ExpressionManager、Canvas、`useFrame` 和鼠标目标 ref。

- **排除的冗余设计及原因：**不引入 AnimationMixer、新依赖、第二个 RAF、后端事件或模型编辑；现有渲染与表达系统足以承载需求。

### 步骤 1：页面级开启交互且保持首页关闭

### 步骤 2：实现模型命中、头身分类和单双击判定

- **涉及文件：**新增 `useVrmAvatarClickInteraction.ts` 与 `useVrmAvatarClickInteraction.test.ts`；修改 `VrmAvatarScene.tsx`

### 步骤 3：将三个动作混入现有动画更新

- **涉及文件：**`useVrmAvatarAnimation.ts`、`useVrmAvatarAnimation.test.ts`
- **实施内容：**提供互斥的 `playGesture`；在现有 `useFrame` 计算带 ease-in/out 的手势时间线；挥手协调右肩、上臂、肘、手腕及轻微躯干倾斜；歪头协调颈部与头部并淡出 pointer look；开心驱动 Happy/Relaxed、两次点头、躯干摆动和轻抬双臂；用 Quaternion slerp 过渡并平滑返回环境姿态。

- **验证方式：**动画时间线与互斥测试；实际加载 `orion.vrm`，按正常页面缩放逐个检查动作幅度、方向、骨骼连接和恢复过程。

## 12. 风险、假设与运行考虑

- **非阻塞假设：**点击头部范围由 Raycaster 命中点相对模型骨骼世界坐标计算，不要求为网格添加额外点击代理。
- **主要风险及应对：**VRM 0.0 的归一化坐标和特定肩臂局部轴可能让初始挥手角方向不合适；本模型节点显示肩臂沿局部 X 轴，先使用局部 Z 抬臂，再以当前模型实际渲染校准符号和上限。通过分阶段角度与 slerp 限制避免突然跳变。
- **性能与清理：**Raycaster 只在用户 click 时运行；复用 Canvas 和 `useFrame`；卸载清除监听器、延迟定时器和表达权重，不新增每帧 React 更新。
- **减少动态效果偏好：**沿用现有动画 Hook 的 `prefers-reduced-motion` 机制，实施时明确直接点击动作与自动 idle 动画的优先级，确保动作约束仍满足。
- **发布、迁移或回滚：**无数据库迁移；回滚只需移除新增点击 Hook 和组件属性传递。
