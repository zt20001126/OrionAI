# 通用对话助手流式输出实现方案

> 日期：2026-10-27（Asia/Shanghai）
> 状态：已实现并完成验证
> 需求确认：已形成方案；兼容性与断连处理按下文非阻塞假设执行

## 1. 目标与背景

- **要解决的问题：** 对话 API 目前通过 `BaseAgent.ainvoke()` 等待整轮模型调用结束，再一次性返回助手消息。`backend/app/shared/streaming/` 已提供通用 SSE 事件、心跳、编码、取消和错误收尾，但 conversations 模块及聊天页面还没有使用它。
- **功能目标：** 让通用对话助手在模型生成普通文本回答时逐段显示内容，并继续支持现有题卡问答、会话标题、历史消息持久化和用户权限规则。
- **预期最终效果：** 用户发送消息后先看到自己的消息，助手回答随模型增量逐步出现；成功结束后页面以数据库中的正式消息替换临时流内容，并刷新历史会话。需要题卡时，页面收到完整题卡并沿用已有答题交互。

## 2. 已确认需求

- **使用者 / 调用方：** 已登录并拥有 `general_chat` 技能的用户；调用方为通用对话页面。
- **触发方式：** 发送普通文本，或提交当前题卡答案。
- **输入：** 复用现有 `MessageCreateRequest` 与 `QuestionAnswersRequest` 请求体。
- **输出：** SSE 的 `start`、`message`、`heartbeat`、`end` 协议事件；`message.data.type` 区分文本增量和题卡内容。
- **主流程：**
  1. 前端通过 `fetch` 向新增流式接口发送带 Cookie 的 POST 请求。
  2. 后端在创建 SSE 响应前完成登录、来源、会话所有权、技能、题卡状态及请求内容校验，并按现有行为提交用户消息。
  3. `BaseAgent` 使用与普通调用相同的 LangGraph 图、线程 ID 和消息 ID 执行本轮；运行时逐步输出模型文本增量。
  4. conversations Service 将 Agent 增量映射为通用 `StreamEvent`；只有整轮结果成功后才保存正式助手文本或题卡消息。
  5. 前端按到达顺序累积文本；收到成功结束事件后重新读取正式消息和历史会话。
- **业务规则与边界：**
  - 流式输出不暴露 reasoning、工具调用参数或内部异常。
  - 题卡不是文本增量；以完整结构化内容交付，仍须完成题卡后才能继续发送。
  - 首轮标题仍由现有标题生成器与 Agent 并行处理，模型失败时沿用首条消息摘要回退。
  - SSE 消息增量是传输态，不单独写入数据库；数据库仍保存完整文本或题卡。
  - 用户切换或离开正在流式输出的页面时可中止客户端请求；前端不自动重发消息。
- **异常行为：** SSE 建立前的校验及业务错误继续返回现有 JSON 错误和 HTTP 状态；响应开始后的 Agent 或持久化失败使用 `end.data.status = "failed"` 结束，不发送异常内容。客户端保留失败状态和可见的部分内容，不自动再次提交。
- **权限与数据范围：** 新接口复用现有 Cookie 登录、`validate_origin`、用户会话所有权和 `general_chat` 校验；会话不存在或不属于当前用户仍返回 404。
- **约束：** 优先复用 `backend/app/shared/streaming/`；不新增框架、依赖、业务表或迁移；保持原 JSON 接口兼容；前端沿用现有对话页布局及全局设计令牌。

## 3. 范围

- **本次包含：** Agent 层流式执行边界；普通消息和题卡答案的新增流式接口；SSE 前端解析和增量渲染；错误、加载、题卡、标题及历史会话回归；API 和架构文档更新。
- **本次不包含：** 删除或改成 SSE 的现有 JSON API；持久化部分回答、流任务状态、重试幂等键、断点续传、文件/图片内容、工具活动面板、模型推理过程、显式的“停止生成”产品控件。

## 4. 需求澄清记录

| 需要确认的问题 | 确认结果 | 对方案的影响 |
|---|---|---|

需求和代码库信息已足够形成方案；上述选择为兼容性和失败处理的明确建议，审阅时可调整。

后端当前数据流为：Router 调用 `ConversationService.send_message()`，Service 先提交用户消息，经 `invoke_agent_from_worker_thread()` 调用 `BaseAgent.ainvoke()`，再保存助手响应。首轮消息另并行执行标题生成。前端当前请求 `conversationApi.ts` 的 JSON 接口，等整轮响应后重新读取消息。

LangGraph 已锁定为 `1.2.17`。官方文档将 `astream_events(version="v3")` 作为应用内事件流接口，提供模型消息增量及最终输出投影；此处用于保留同一图执行、检查点和工具路由，避免“先流式生成、再调用一次 `ainvoke`”造成重复推理。见 [LangGraph Event streaming](https://docs.langchain.com/oss/python/langgraph/event-streaming) 和 [LangGraph Streaming](https://docs.langchain.com/oss/python/langgraph/streaming)。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| `agent/runtime/base_agent.py` | 增加 `astream()`，执行现有图并产出内部文本增量与最终 `AgentResponse` | Agent Runtime 只依赖 LangGraph 和 Agent schema；不认识 SSE、FastAPI 或 ORM |
| `agent/schemas.py` | 定义 Agent 内部 `text_delta`、`result` 等流事件 | 为 Agent 与业务编排提供类型；不是 HTTP DTO |
| `modules/conversations/router.py` | 暴露新增 POST 流式接口、复用认证与来源校验，并在响应头发送前完成业务预检 | Router 不解析模型 token、不负责消息持久化 |
| `modules/conversations/service.py` | 复用现有权限/技能/题卡检查与用户消息写入；将 Agent 事件映射为共享 `StreamEvent`；完成后保存助手消息和标题 | conversations 业务继续拥有持久化与业务事件语义 |
| `modules/conversations/schemas.py` | 声明 SSE `message.data` 的业务 payload 类型 | 对外协议定义留在 conversations 模块，最终消息继续复用 `MessageResponse` |
| `shared/streaming/` | 包装开始、心跳、结束、帧编码及取消清理 | 保持业务无关，不导入 Agent/conversations |
| 前端 `conversationApi.ts` | 携带 JSON 请求体、Cookie 和 `AbortSignal`，按 SSE 帧解码事件 | 这是 POST 请求，使用 Fetch `ReadableStream`，不使用只适合 GET 的 `EventSource` |
| 前端 `ConversationPage.tsx` | 维护本轮临时文本、状态及失败标记；成功后同步数据库真值 | 继续复用已有题卡组件、会话历史刷新与滚动行为 |

### 关键流程

```text
ConversationPage
  -> POST /api/conversations/{id}/messages/stream 或 /answers/stream
  -> Router：登录与 Origin 校验；Service 预检并提交用户消息
  -> create_sse_response(Service async event source)
  -> Service：BaseAgent.astream(thread_id, message_id)
  -> LangGraph astream_events(version="v3")
       ├─ agent_node 的模型文本增量 -> StreamEvent MESSAGE(text_delta)
       └─ graph 最终状态 -> AgentResponse(completed / waiting)
  -> Service 保存完整助手消息；题卡则保存完整 question part
  -> StreamEvent MESSAGE(question，可选) -> StreamEvent END(completed)
  -> 前端读取正式消息与会话标题，替换临时增量
```

具体约定：

1. **Agent 流式运行：** `BaseAgent.astream()` 复用 `_prepare_runnable_config()`、相同 `thread_id` 和 `message_id`，调用当前已编译图的异步事件流。只转发 `agent_node` 的文本投影；过滤 reasoning、tool-call chunks 和非文本块。通过事件流最终输出构造现有 `AgentResponse`；不再另行调用 `ainvoke()`。
2. **协议映射：** 使用现有公共 `StreamEvent`。业务消息事件至少定义：`{"type":"text_delta","content":"..."}`；题卡定义为完整 `{"type":"question","message": <MessageResponse>}`。普通文本完成后由通用 `end.status=completed` 表示成功，前端随即读取正式消息；题卡事件只在题卡已持久化后发送。`end.status=failed` 不携带模型异常详情。
3. **响应开始前校验：** 新增端点在构造/返回 `StreamingResponse` 之前执行所有会影响 HTTP 状态的业务预检。这样未登录、无权访问、未添加技能、当前正在等待题卡、答案无效和数据库不可用仍返回现有 401/404/409/422/503 语义；模型调用与最终提交发生在流开始后时，错误通过安全的 `end.failed` 表达。
4. **持久化与标题：** 保持先提交用户消息、完成后提交完整助手消息的顺序。首轮标题生成和 Agent 调用并行，首轮 SSE 在标题保存或回退完成后正常收尾，保留历史列表刷新行为。运行中的 token 不写入 `messages.content`。
5. **前端读取：** 解析器按空行识别帧，支持 UTF-8 多字节字符和 JSON 帧被任意网络块拆分；遇到 `start`、`heartbeat` 时不改业务内容，按顺序处理 `message`，仅在 `end.completed` 后执行成功刷新。`end.failed` 或网络断开时展示错误状态且不自动重发。
6. **断连边界：** 复用公共流实现的取消/关闭逻辑。用户消息已在生成前提交，因此中断时可能只保留该用户消息；不保存残缺助手回答。当前页面保留的部分文本标为未完成，重新打开历史时显示数据库已有消息，不伪造完整答复。

LangGraph 版本已有推荐的事件流 API，并能单独读取模型消息增量和最终状态；相比直接观察 `stream_mode` 原始分块，它减少对内部协议的耦合。若 Agent 事件投影在实际锁定版本中无法满足题卡最终状态读取，再退回同版本 `astream(stream_mode=["messages", "updates"], version="v2")`，不新增依赖或改图结构。

## 9. 接口与数据库变更审查

### 接口影响

| 接口（方法 + 路径 / 事件） | 操作 | 当前定义位置 | 变更前后契约 | 复用判断与变更理由 | 兼容性 / 调用方影响 |
|---|---|---|---|---|---|
| `POST /api/conversations/{id}/messages` | 保持不变 | `backend/app/modules/conversations/router.py` | 继续接收 `{"message": ...}` 并返回 `AgentTurnResponse` JSON | 复用既有同步接口，避免将公开响应类型从 JSON 改为 SSE | 既有调用方无影响 |
| `POST /api/conversations/{id}/messages/stream` | 新增 | 同上 | 同一请求 DTO；返回 `text/event-stream`，包含 `start`、零到多条 `message(text_delta)`、必要心跳和 `end`；业务失败时 4xx/5xx 预检或 `end.failed` | SSE 和 JSON 的响应体互斥，不能在原路径同时保持稳定 JSON 契约；新增端点提供兼容接入 | 当前 React 页面改用新端点；其他调用方可继续用 JSON |
| `POST /api/conversations/{id}/answers` | 保持不变 | 同上 | 继续接收 `{"answers": ...}` 并返回 `AgentTurnResponse` JSON | 既有题卡 API 保持同步兼容 | 既有调用方无影响 |
| `POST /api/conversations/{id}/answers/stream` | 新增 | 同上 | 同一答案 DTO；题卡恢复后的助手文本增量以 SSE 返回 | 用户完成题卡后仍使用相同 LangGraph 线程，但可逐步显示后续回答 | React 页面切换到新端点；原端点不变 |
| `GET /api/conversations`、`GET /api/conversations/{id}/messages`、`POST /api/conversations` | 保持不变 | 同上 | 会话列表、消息结构和空会话创建均不变 | 复用正式持久化结果读取，不在 SSE 中重定义历史数据格式 | 无影响 |
| SSE `message` 业务 payload | 新增协议内容 | `backend/app/modules/conversations/schemas.py`（拟修改） | `text_delta` 带 `content`；`question` 带完整已保存的 `MessageResponse`。SSE 外层仍为共享 `StreamEvent` envelope | 共享事件仅规定 message payload 有 `type`，业务字段应由 conversations 领域定义 | 仅流式端点消费者需实现解析；未知 `message.data.type` 应忽略而非崩溃 |

流式写接口继续受 Cookie 和来源校验保护；请求体复用 JSON DTO；不新增权限、字段校验或题卡规则。SSE 一旦发送响应头后不能再改变 HTTP 状态，因而预检必须在响应对象返回前完成。

### 数据库影响

| 表 / 字段 | 操作 | 当前定义位置 | 用途与需求依据 | 复用判断与新增理由 | 迁移 / 回填 / 默认值 / 回滚 |
|---|---|---|---|---|---|
| `conversations.id`、`user_id` | 保持不变 | `backend/app/modules/conversations/models.py` | 定位当前用户拥有的会话及 LangGraph 线程 | 现有主键和所有权关联满足需求 | 无迁移 |
| `conversations.title`、`updated_at` | 保持不变 | 同上 | 首轮标题回退/保存及对话活动排序 | 现有标题生成和时间更新逻辑可复用 | 无迁移或回填；保留原值 |
| `messages.id`、`conversation_id`、`role`、`content`、`created_at` | 保持不变 | 同上；消息结构见 `backend/app/modules/conversations/schemas.py` | 提交用户消息，并仅保存生成完成后的文本或完整题卡 | 现有 JSONB `parts` 结构可以保存最终消息；token 只属于临时传输态 | 无迁移、回填或默认值变更；回滚代码后原消息仍可读 |
| LangGraph Checkpointer 内部状态表 | 保持不变 | 由现有 `AsyncPostgresSaver` 管理 | 通过同一个 thread ID 延续对话和题卡状态 | 流式执行沿用现有图与 Checkpointer，不新增运行状态表 | 无业务迁移；共享检查点的取消边界列入验证和风险 |

### 最小变更结论

- **可复用的现有接口 / 数据结构：** `MessageCreateRequest`、`QuestionAnswersRequest`、`AgentResponse`、`MessageResponse`、现有所有权和技能校验、会话消息 `parts`、LangGraph Checkpointer，以及共享 `EventType`/`StreamEvent`/`create_sse_response()`。
- **本方案实际新增或修改的最小集合：** Agent 流式门面及内部事件类型；两个兼容型 SSE 端点；Service 的流式编排；前端 Fetch SSE 解码与增量渲染；相关回归和契约文档。
- **排除的冗余设计及原因：** 不修改原 JSON 接口、不增加数据库状态/部分答案、不保存 token 日志、不引入 EventSource polyfill 或额外前端依赖；现有 schema、Fetch 和通用 SSE 足以覆盖行为。
- **尚未确认的接口或数据决策：** 无阻塞项。若后续要求断点续传、部分回答跨刷新恢复或客户端安全重试，再单独定义幂等键/运行状态及相应存储方案。

## 10. 分步实施计划

### 步骤 1：为 BaseAgent 增加流式执行门面

- **目的：** 在同一 LangGraph 执行中同时取得模型文本增量和本轮最终结果。
- **涉及文件：** `backend/app/agent/runtime/base_agent.py`、`backend/app/agent/schemas.py`、`backend/tests/unit/test_base_agent.py`。
- **实施内容：** 增加 Agent 内部增量与结果事件；使用 LangGraph `astream_events(version="v3")`；过滤目标节点的文本消息；从最终图输出复用现有 completed/waiting 转换；保证取消时关闭事件流。旧 `ainvoke()` 不变。
- **前置依赖：** 无。
- **验收标准：**
  - [ ] 普通测试模型产生的多段文本按原顺序形成增量事件，事件结果中的 `AgentResponse.answer` 与完整图输出一致。
  - [ ] 工具调用参数、reasoning 和非文本内容不会出现在 Agent 用户文本事件中。
  - [ ] `ask_user_questions` 仍返回 `waiting` 及原结构化题卡，且流执行与 JSON 执行使用相同 thread/message 标识约定。
  - [ ] 消费者取消流时，底层 LangGraph/模型迭代器被关闭；未增加第二次模型调用。
- **验证方式：** 扩展 `test_base_agent.py` 覆盖完成、题卡、过滤与取消；按项目规则执行类型/静态检查。

### 步骤 2：新增兼容型对话 SSE API

- **目的：** 将 Agent 增量映射为 SSE，同时保留已有事务、授权、标题和消息语义。
- **涉及文件：** `backend/app/modules/conversations/router.py`、`service.py`、`schemas.py`、`backend/tests/integration/test_conversation_endpoints.py`。
- **实施内容：** 增加 `/messages/stream` 与 `/answers/stream`；先完成请求预检并保存用户消息，再返回 SSE 响应；映射文本增量和题卡结果；成功后只写入完整助手消息。首轮标题与 Agent 并行，失败沿用摘要回退。共享 `create_sse_response()` 负责协议生命周期、心跳和失败收尾。
- **前置依赖：** 步骤 1。
- **验收标准：**
  - [ ] 新增接口的响应 Content-Type 为 `text/event-stream`，有效普通回复中按生成顺序含文本增量，最后只有一个 `end.completed`。
  - [ ] 题卡等待事件在完整题卡消息持久化后发出；通过 `/answers/stream` 恢复后可得到文本增量和正式助手消息。
  - [ ] 未登录、其他用户会话、未添加技能、待答题卡阻止发送、无效答案分别保留现有 HTTP 错误语义，且流响应头开始前不会返回 200 SSE。
  - [ ] Agent 失败时发出安全的 `end.failed`，异常文本和堆栈不出现在帧中；用户消息保留，部分助手内容不写入数据库。
  - [ ] 原 JSON 消息和答案端点仍返回原 `AgentTurnResponse`，标题生成和历史消息内容不变。
- **验证方式：** 使用现有 SQLite API 集成夹具及假 Agent；检查完整 SSE 帧序列、持久化消息、权限和预检错误。共享 SSE 的取消行为由既有 `test_streaming.py` 覆盖。

### 步骤 3：将对话页改为消费流式接口

- **目的：** 让用户在模型生成时即可阅读回答，并在结束后恢复持久化真值。
- **涉及文件：** `frontend/src/features/conversations/conversationApi.ts`、`ConversationPage.tsx`、`conversations.css`、`frontend/tests/Conversations.test.tsx`。
- **实施内容：** 增加 Fetch SSE 解析器与业务事件类型；支持 request body、Cookie、`AbortSignal`、UTF-8 多字节字符和跨 chunk 帧缓存；页面累积文本增量，显示流状态；处理题卡、失败和页面切换取消；成功后刷新消息和历史。将旧“回答以完整消息形式返回”提示改成符合流式行为的文案。
- **前置依赖：** 步骤 2。
- **验收标准：**
  - [ ] 在 SSE 流尚未结束时，页面已显示助手逐段回答；用户输入和重复提交仍按现有规则禁用/保护。
  - [ ] SSE 帧被拆成任意网络块、中文 UTF-8 字符跨块时，事件文本仍完整且顺序正确。
  - [ ] `end.completed` 后正式助手消息替换临时内容，题卡页面可交互，历史会话显示最新标题和时间。
  - [ ] `end.failed`、HTTP 错误、读取中断各自显示可理解的错误；不自动重发，不把部分回答误标成已完成。
  - [ ] 页面切换/卸载会中止当前请求；既有题卡选择、会话切换、自动滚动和响应式布局行为保持可用。
- **验证方式：** 扩展 `Conversations.test.tsx`，以模拟 `ReadableStream` 发送分块帧并检查增量可见、完整刷新、失败及取消。检查 UI 继续使用 `UI_DESIGN.md` 的中性底色、品牌蓝和主题令牌。

## 12. 风险、假设与运行考虑

- **非阻塞假设：** 现有 JSON API 仍是兼容入口；通用对话页改用新增 SSE API。普通文本和题卡答案都支持流式，题卡作为完整消息事件。页面切换会中止请求，但不新增显式停止按钮。
- **断连一致性风险：** 用户消息在调用模型前已提交；如果客户端中途断开，可能留下没有助手回复的用户消息，且图检查点可能处于未完成轮次。方案不自动重试或持久化部分文本，页面重新打开后以数据库记录为准。若产品要求可靠续传/幂等重试，需要增加明确的运行状态或请求幂等设计，不能仅靠 SSE 帧 ID 实现。
- **Agent 完成态风险：** 文本增量和最终 `AgentResponse` 必须来自同一次图执行。实现中不可为了获得最终消息再执行 `ainvoke()`；测试需覆盖 Checkpointer 下正常完成和题卡等待两条分支。
- **SSE 代理缓冲：** 共享响应已设置 `X-Accel-Buffering: no` 与 `Cache-Control: no-cache, no-transform`；部署代理仍须保持 HTTP 流式转发且不做响应缓冲。当前开发通过 Vite `/api` 代理，部署 nginx 配置属于预留目录，本次不额外新增代理配置，若生产环境已有代理需人工确认。
- **错误与日志：** 共享层仅向客户端发送 `end.failed`；服务端沿用异常类型日志，不记录消息原文、事件内容、Cookie 或密钥。
- **数据库 / 发布：** 无数据库迁移和数据回填；后端先发布新增兼容接口，再发布会调用它的前端即可。回滚前端后旧 JSON 接口仍可用；回滚后端时需同时回滚/禁用依赖 SSE 的前端版本。
