# 数字人对话多方式路线规划实现方案

> 日期：2026-11-12（Asia/Shanghai）
> 状态：已实施
> 需求确认：已澄清

## 1. 目标与背景

- **要解决的问题：**数字人聊天路线工具目前只会调用步行规划，而且要求输入已经是高德 GCJ-02 坐标；用户不能在对话中选择步行、骑行或驾车，也不能直接用自然语言地址完成路线规划。
- **功能目标：**让数字人对话支持步行、骑行、驾车三种路线；用户未说明方式时，通过现有提问卡片询问，明确方式后调用对应高德路线接口。
- **预期最终效果：**用户可以用自然语言提出起点、终点和出行方式；缺少出行方式时先看到路线类型题卡，选择后恢复对话并规划。使用“当前位置”时先取得明确浏览器定位授权；完成后在消息历史中看到对应类型、距离、耗时、步骤、路线静态图和高德导航入口。

## 2. 已确认需求

- **使用者 / 调用方：**数字人聊天用户；数字人 LangGraph Agent 调用高德服务。
- **触发方式：**用户在数字人对话中提出路线规划需求。
- **输入：**用户自然语言中的出行方式、起点和终点；缺失信息通过现有题卡补齐。起终点可以是结构化地址/地标，起点也可以是明确授权后的当前位置。
- **输出：**统一结构的路线结果，包含方式、端点名称及 GCJ-02 坐标、距离、耗时、分步指示和可选轨迹；用于对话消息持久化、路线卡片及静态图。
- **主流程：**
  1. Agent 判断出行方式和端点是否明确；未提供方式时调用 `ask_user_questions` 展示三种方式及“暂不规划”选项，之后等待用户答题。
  2. 起终点文本通过高德地理编码解析为坐标；当前起点只有在用户明确同意浏览器定位后才读取 WGS-84 坐标，并转换成 GCJ-02。
  3. Agent 调用统一的路线规划工具；工具按方式选择高德步行、骑行或驾车 V5 接口，并把不同响应转换为现有路线结果结构。
  4. Runtime 提取本轮路线结果，Conversation Service 按既有 `route_result` 消息格式保存并通过现有会话流返回。
  5. 前端按路线方式渲染标题与导航链接；复用现有路线步骤、静态地图和历史恢复能力。
- **业务规则与边界：**只支持 walking、bicycling、driving；用户已明确方式时不再询问。单选题卡底层固定要求四个选项，因此第四项用“暂不规划”，不代表新增路线方式。起点或终点未提供时继续询问，不推测地址；地理编码无结果或无法可靠区分时要求补充地址。IP 粗定位仅能估计城市，不得作为路线起点。
- **异常行为：**拒绝定位、定位不可用、地理编码失败/不明确、路线无结果、高德超时或返回无效数据时，不生成虚假路线；Agent 明确告知并按情况询问用户补充信息或授权。
- **权限与数据范围：**当前位置继续使用已存在的浏览器授权题卡及本轮位置上下文；API Key 只在服务端使用。路线消息仍按当前做法持久化，历史中的路线坐标和轨迹供地图恢复使用；不新增个人位置专用表或配置。
- **约束：**仅改造对话中发起的路线规划。周边商家卡片“路线规划”按钮及其 `/walking-route/stream` 仍保持步行行为，不纳入本次需求；不增加公交、电动车路线和新依赖。

## 3. 范围

- **本次包含：**路线类型题卡规则、自然语言端点解析、浏览器定位授权与坐标转换、三种高德 Web 服务路线接口、统一 Agent 工具及结果结构、路线结果 UI 与导航 URI、相关测试。
- **本次不包含：**周边商家卡片按钮的路线方式选择、公交/电动车、多候选路线比较、语音专用路线流程、数据库结构调整。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| `agent/capabilities.py` | 规定路线意图何时询问方式、何时请求定位/地址，以及何时调用规划工具。 | 只描述 Agent 决策，不写外部 API 逻辑。 |
| `agent/tools/route_planning.py`（拟新增） | 接收方式和用户表达的起终点；读取当前运行的授权位置上下文；编排地理编码、坐标转换和算路；返回统一工具结果。 | Agent Tool 调用 `providers/amap`，不直接发 HTTP。 |
| `providers/amap/geocoding.py`（拟新增） | 使用 `/v3/geocode/geo` 把地址或地标转为 GCJ-02 坐标；无法确定时给出可处理错误。 | 只封装高德协议、超时和响应校验。 |
| `providers/amap/route_planning.py`（拟新增） | 按 `mode` 调用 `/v5/direction/walking`、`/v5/direction/bicycling` 或 `/v5/direction/driving`，解析为统一路线结构。 | 只处理第三方接口；保留当前商家按钮的独立步行客户端。 |
| `providers/amap/coordinates.py`（拟新增） | 规范化坐标并复用 `/v3/assistant/coordinate/convert` 转换浏览器 GPS 坐标。 | 由新路线 Provider、旧步行 Provider 和静态地图 Provider 复用，避免把转换逻辑留在步行专属类中。 |
| `agent/runtime.py` 与会话 schema/service | 识别新工具结果并走既有 `route_result` 结构。 | 不新增 API 编排或独立存储。 |
| 数字人消息 UI | 根据 `route.mode` 显示步行/骑行/驾车并组装 URI 路线方式。 | 继续使用现有问题卡片、路线消息和静态图接口。 |

### 关键流程

```text
用户聊天
  -> DigitalHuman Agent
  -> 未提供方式：ask_user_questions（步行/骑行/驾车/暂不规划）并等待
  -> 缺少端点：用现有 Text 题卡补齐；“当前位置”使用现有定位授权题卡
  -> plan_route
  -> 地址/地标 geocode，或授权位置 WGS-84 转 GCJ-02
  -> 高德对应 mode 的 V5 路线接口
  -> AgentRuntime 提取 route_result
  -> ConversationService 保存现有消息 part
  -> 数字人路线卡片 + 静态地图 + 对应高德 URI
```

**模式一致性：**Agent 工具 `mode` 采用固定枚举，能力提示要求只有用户已明确指定或已在题卡中选择后才能调用。选择“暂不规划”时不调用高德。模型不得推测坐标；地址解析无结果或歧义时通过 Text 题卡补问。若起点为当前位置，沿用 `digital_human_location_consent` 的授权题：只有选中允许后页面才请求浏览器定位；服务端从本轮 `user_location` 读取 WGS-84 并转为 GCJ-02。拒绝或不可用时不能用 IP 粗定位代替。

**路线数据统一：**三种 V5 响应都映射到 `mode`、`origin`、`destination`、`distance_m`、`duration_s` 和 `steps`。请求显式包含 cost、navi、polyline 字段；返回缺少必要距离、耗时或步骤时按无效路线处理，不用 0 或空步骤掩盖失败。默认展示高德首选路线，保持现有单路线卡片结构。

**高德文档依据：**路径规划 V5 支持所需三种方式，入口分别为 walking、bicycling、driving；[路径规划 2.0](https://lbs.amap.com/api/webservice/guide/api/newroute)。地理编码可将结构化地址和地标转换为高德坐标；[地理/逆地理编码](https://lbs.amap.com/api/webservice/guide/api/georegeo/)。高德导航 URI 对应方式为 `walk`、`ride`、`car`；骑行 URI 仅移动端有效，[URI 路径规划](https://lbs.amap.com/api/uri-api/guide/travel/route)。

## 9. 接口与数据库变更审查

### 接口影响

| 接口（方法 + 路径 / 事件） | 操作 | 当前定义位置 | 变更前后契约 | 复用判断与变更理由 | 兼容性 / 调用方影响 |
|---|---|---|---|---|---|
| `POST /api/conversations/{conversation_id}/runs/messages` | 保持不变 | `conversations/router/router.py` | 仍接收用户自然语言消息并创建 Agent 运行；缺少 mode 时由 Agent 回题卡。 | 已有对话启动接口足以承载，不新增专用路线接口。 | 前端请求契约不变。 |

### 最小变更结论

- **可复用的现有接口 / 数据结构：**通用 `ask_user_questions` 题卡和暂停/恢复；`QuestionAnswersRequest` 的定位上下文；`route_result` part、Conversation SSE、静态地图接口；现有高德 Key 和 GPS 坐标转换。
- **本方案实际新增或修改的最小集合：**一个通用 Agent 路线工具、地理编码和多模式 Provider、通用坐标模块、路线 mode schema 及前端卡片映射。
- **排除的冗余设计及原因：**不新增 HTTP 路线规划接口或 DB 字段；不为模式选择创建独立前端题卡协议；不把用户当前位置走 IP 城市估计；不改周边商家按钮路线流程。
- **尚未确认的接口或数据决策：**无。首选路线按高德默认结果展示；地址不唯一时先向用户补问。

## 10. 分步实施计划

- **目的：**将当前步行客户端里的坐标规范化和 GPS 转换用于新的聊天路线模式，按地址和 mode 调用正确的高德接口。

## 12. 风险、假设与运行考虑

- **非阻塞假设：**起终点若是用户当前所在位置，需显式提出“当前位置”意图；没有明确起点时 Agent 询问，不默认获取定位。地点解析上下文优先使用用户已提供的城市/区县；解析不确定时先澄清。
- **路线结果：**按高德默认首选方案显示单条路线；本次不做多方案比较或策略选项。高德数据变化可能使同一地址路线变化，符合现有路线服务特性。
- **定位与隐私：**浏览器定位必须走已存在的授权题卡；粗略 IP 城市不能作为路线坐标。成功路线消息仍会保存端点坐标和轨迹以支持历史地图，这是现有 `route_result` 结构的既有用途。
- **导航 URI：**高德 URI 的骑行模式仅移动端有效；桌面端仍展示内部路线结果/静态图，导航链接能力按高德客户端行为受限。
- **发布 / 回滚：**无需 Alembic migration 或新环境变量；回滚代码前需关注已保存的 bicycling/driving 消息，因为旧 schema 只接受 walking。可保留向后兼容的 mode 读取，或在回滚前确认未产生新 mode 消息。
