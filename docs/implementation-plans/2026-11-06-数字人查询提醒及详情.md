# 数字人查询当前用户提醒及详情方案

> 日期：2026-11-06  
> 状态：待审阅

## 目标与范围

数字人能够列出当前用户的提醒，按提醒状态筛选，并查询某一条提醒的详情。身份由服务端会话上下文提供；模型不能指定用户 ID，任何情况下都不能返回其他用户的提醒。

本方案查询提醒规则及其状态；邮件的每次执行和发送结果属于执行记录，暂不纳入。复用现有分页、详情服务和题卡，不新增图节点、公开接口或数据库结构。

## 当前实现依据

- `backend/app/modules/reminders/service.py`：`ReminderService.list(user, query)` 和 `get(user, reminder_id)` 分别提供列表与详情。
- `backend/app/modules/reminders/repository.py`：列表使用 `Reminder.user_id == user_id` 过滤；详情同时使用提醒 ID 与用户 ID 过滤。
- `backend/app/modules/reminders/schemas.py`：`ReminderListQuery` 支持状态、`limit` 和 `offset`；`ReminderResponse` 包含标题、内容、类型、重复配置、时区、状态、下次执行时间等。
- `backend/app/modules/conversations/service/service.py`：数字人的运行配置注入可信 `user_id` 和 `conversation_id`；会话运行入口有会员准入要求。
- `backend/app/modules/digital_human/agent/tools/reminder.py` 已包含创建工具；`graph.py` 注册工具，`capabilities.py` 描述模型能力。

## 用户流程与工具设计

1. 用户询问“我有哪些提醒”时，模型调用新增 `list_reminders`，默认不按状态过滤；“启用中/暂停/取消/完成”映射为 `active`/`paused`/`cancelled`/`completed`。工具从可信配置读取当前用户，调用 `ReminderService.list`，返回本页记录、总数、偏移量和是否还有下一页。
2. 列表默认每页 20 条，最多每页 100 条，顺序沿用现有服务的创建时间倒序。同一会话可继续请求下一页；每页只返回必要摘要，并明确“本页 X 条、共 Y 条、是否还有更多”，不得把第一页说成全部。用户要求查看全部时可继续逐页查询，但不能声称已展示尚未查询的数据。分页期间数据变化可能影响顺序与总数，不承诺快照一致性。
3. 用户询问某条详情时，若已有明确提醒 ID，调用新增 `get_reminder`；若只有标题，先逐页查询当前用户列表进行匹配，唯一匹配后读取详情，多条匹配则通过现有题卡让用户选择。未遍历全部页面前不能断言没有匹配；若查询量或执行限制使遍历无法完成，说明范围并请用户提供更多信息，不猜测。现有列表不支持数据库按标题搜索，不在本次新增该功能。
4. 详情通过 `ReminderService.get` 获取，展示可用的标题、内容、类型、重复规则、状态、时区、下次执行时间、结束日期及创建时间。`next_run_at` 是 UTC，展示时依据记录的 IANA 时区转换；为空时说明当前没有下一次计划，不编造日期。一次性提醒的 `repeat_config` 为空，不能假定历史计划日期总能从该字段还原。
5. 列表为空时说明当前筛选条件没有记录；详情不存在或不属于当前用户时返回同一条“提醒不存在或不可用”，避免泄露资源是否存在。服务故障返回明确失败，不伪装成空列表。

## 权限与资源边界

两个查询工具都从 `RunnableConfig` 的服务端 `user_id` 加载真实用户，并使用独立数据库会话、及时关闭。模型参数不包含用户 ID；即使传入其他用户的提醒 ID，现有 Repository 的用户过滤也使其不可见。会话入口现有会员要求保持不变；提醒读取 API 本身只要求当前登录用户，查询工具无需照搬创建工具的额外会员检查。若可信上下文缺失或用户不存在，应返回失败并停止查询。

列表工具使用结构化结果返回 ID、标题、状态、类型及下次计划；详情工具返回 `ReminderResponse` 的必要字段。提醒 ID 以十进制字符串传递，按现有 Snowflake 上限校验后再转为整数。日志不记录提醒正文或用户凭据。

## 接口与数据库影响

| 接口或资源 | 操作 | 原因与兼容性 |
|---|---|---|
| `GET /v1/reminders` | 不变 | 新工具直接调用同一个 `ReminderService.list`；现有 HTTP 契约不变。 |
| `GET /v1/reminders/{reminder_id}` | 不变 | 新工具复用 `ReminderService.get`；现有 HTTP 契约不变。 |
| `POST /conversations/{conversation_id}/runs/messages` 和 `/runs/answers` | 不变 | 继续使用现有对话和题卡协议。 |
| 内部工具 `list_reminders` / `get_reminder` | 新增 | 分别承载当前用户分页查询与指定提醒详情。 |
| `reminders` 表及其字段 | 不变 | 已有用户归属、提醒规则、状态和计划字段足以支持本次需求；无需迁移或回填。 |
| `reminder_executions` 表 | 不变 | 本次不查询执行历史。 |

## 实施步骤与验收

1. **实现列表及详情工具。** 修改 `tools/reminder.py`，复用服务及输入约束。验收：用户 A 的列表和详情无法读取用户 B 的记录；列表支持状态和分页，空结果、无权详情、基础设施错误可区分；详情时间带正确时区，空下次时间不编造。
2. **接入数字人。** 修改 `graph.py` 和 `capabilities.py`。验收：模型可使用两个工具；默认查询全部状态，支持下一页；同名提醒通过题卡选择，未完成全量查找时不误报无结果。
3. **验证回归。** 扩展列出的单元测试，并运行数字人图、提醒工具和提醒 Service 相关测试及适用静态检查。验收：跨用户隔离、分页总数、状态筛选、缺失和服务异常通过；已有创建提醒和邮件题卡行为通过回归。真实模型对自然语言的提取还需人工验收，自动化图测试使用受控模型输出。

## 假设与限制

- 用户询问“全部”时以分页方式展示，能够继续读取所有当前用户记录，不保证单次模型调用可以承载任意数量数据。
- 重复标题需要用户选择；现有数据库接口不支持按标题过滤，逐页匹配受运行次数和数据量限制。
- 本次不增加发送结果查询、不修改提醒创建流程。所有测试为实施计划，尚未执行。
