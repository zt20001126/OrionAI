# 评论结果情感字段实现方案

> 日期：2026-11-04（Asia/Shanghai）  
> 状态：已实现  
> 需求确认：已澄清；按现有分析结果项附加情感标签

## 1. 目标与背景

- **要解决的问题：** 现有分析结果显示评论证据和规则匹配状态，但没有显示该结果项对应内容的情感倾向。
- **功能目标：** 对 Agent 输出的每条现有分析结果项增加情感判断，并在结果页显示“正向、负向、客观”之一。
- **预期最终效果：** 每条结果明细除现有证据、匹配状态和评分规则外，再显示一个情感值；不显示整条评论的总体情感。

## 2. 已确认需求

- 情感判断针对智能体拆分评论后形成的分析结果项，不针对整条原评论。
- 分类值固定为 `positive`、`negative`、`objective`，前端显示为正向、负向、客观。
- 仅在最终“分析结果”页面展示；不新增输入项、筛选、统计或趋势图。
- 旧结果保留，新增情感字段为空，不回填历史数据。
- 不改变 API 路径、评分规则、匹配规则、会话协议和业务范围判断。

## 3. 当前结构与重要实现边界

当前 Agent 在 `backend/app/modules/agents/tourism_insight/schemas.py` 定义 `ReviewFact`（拆分事实）和 `MatchCandidate`（包含规则 ID、证据、匹配依据、匹配状态）。`analyze.py` 将结构化候选放入 `AnalysisContext.validated_matches`，`persist_reply.py` 把这些候选交给业务 Service。`backend/app/modules/tourism_insight/models.py` 的 `CommentMatch` 保存每条结果，`GET /api/tourism-insight/results` 由 Service 返回给 `AnalysisResults.tsx` 展示。

因此最小设计是在现有 `MatchCandidate` / `CommentMatch` / `MatchResponse` / TypeScript 结果项上加一个 `sentiment` 字段，不增加段落文本、段落序号或新表。现有 `evidence` 继续作为结果项所对应的评论原文片段。

**实现边界说明：** 当前 `CommentMatch` 记录的是一条规则匹配结果；提示词允许一个事实匹配多个评分子项，所以同一证据可能在多条结果项中出现。按本方案，情感跟随现有结果项保存和展示；如果同一证据对应多个评分项，标签会随各结果项重复。这符合“在原本结果上直接增加字段”的粒度。若将来要求同一拆分事实只显示一次并聚合其多个评分项，需要另行增加结果项之间的事实关联，本次不做。

## 4. 架构设计

### 数据与控制流

```text
现有评论分析
  -> Agent 结构化匹配输出增加 sentiment
  -> analyze 节点校验候选、证据和三值情感
  -> 现有 CommentMatch 保存 sentiment
  -> 现有 GET /api/tourism-insight/results 返回 sentiment
  -> AnalysisResults 在每条结果明细旁显示标签
```

情感字段由 Agent 结构化输出生成，程序负责校验它只属于三个允许值；不由前端根据词语推断。对没有可拆分事实的兜底结果，`sentiment` 可为空。对模型无法按结构返回分类的情况，沿用既有分析失败处理，不写入一个伪造的“客观”值。

### 为什么复用现有结果结构

- `UgcComment` 保存原始评论，整条评论可能同时含正负面内容，不能承载段落级结果。
- `CommentMatch.status` 表示评分规则是否匹配，语义与情感不同；不能复用。
- `CommentMatch.evidence` 已保存结果对应的原文片段；本需求没有要求保存新的段落摘要，所以不增加 `fact` 字段。
- 本次展示沿用每条现有分析结果作为单位；不需要 `fact_index` 或额外关系表。

## 6. 接口与数据库影响

### 接口

| 接口 | 操作 | 契约及影响 |
|---|---|---|
| `GET /api/tourism-insight/results?limit=&offset=` | 修改响应 | 每条现有 `matches[]` 结果增加可空 `sentiment`；路由、参数、权限和其他字段不变。调用方可忽略新增字段。 |
| `POST /api/tourism-insight/analyses` | 保持不变 | 仍返回逐条分析状态；详细结果继续由 GET results 获取。 |
| 会话消息发送与 SSE | 保持不变 | 仅存储的分析结果增加情感值；对话消息响应协议不变。 |

### 数据库

| 表 / 字段 | 操作 | 用途与迁移 |
|---|---|---|
| `comment_matches.sentiment` | 新增 nullable `String(20)` | 表示当前结果项的正向、负向或客观分类；增加三值检查约束。旧行自动为 `NULL`，无历史回填。回滚删除约束和列。 |
| `scoring_rules`、`ugc_comments` 及其他 `comment_matches` 字段 | 保持不变 | 规则、原评论、证据、匹配状态和历史结果原样保留。 |

沿用现有 `comment_matches` 和 `GET results`，不新增表、段落字段或 API。`repository.replace_comment_matches` 已通过结果字典创建 ORM 记录，可继续复用；需要核对新增字段从 Agent 到 Repository 的传递完整性。

## 8. 风险、假设与运行考虑

- **粒度假设：** 标签附加到当前 `MatchCandidate` / `CommentMatch` 分析结果项。一个拆分内容若匹配多个评分项，可能在多个结果项各显示一次标签；本方案不做跨结果归并。
- **“客观”定义：** 没有明确正面或负面评价、主要是事实描述的内容。模型无法产生有效分类时不得默认为客观。
- **迁移：** 仅加 nullable 列和允许值约束，无回填；已有评论、匹配行和 ID 保持不变。迁移在部署时按现有 Alembic 流程执行，开发数据库不由本方案直接操作。
- **回滚：** 可删除新增列和约束；回滚后情感值丢失，其余历史匹配数据保持不变。
