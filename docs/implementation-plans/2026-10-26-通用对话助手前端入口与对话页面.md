# 通用对话助手前端入口与对话页面实现方案

> 日期：2026-10-26（Asia/Shanghai）  
> 状态：待审阅  
> 需求依据：`docs/requirements/2026-10-26-001-general-conversation-assistant-frontend.md`；含已标注的非阻塞假设

## 1. 目标与范围

- **目标**：让登录用户从“我的智能体”的“通用对话助手”卡片进入对话页，发送文本、处理单选题卡、查看并继续自己的历史会话；侧栏“会话记录”也可进入历史列表。
- **包含**：卡片入口与明确未开放的添加控件、空白对话、新会话与多轮消息、题卡提交、历史列表与切换、加载/空/失败状态、路由和回归测试。
- **不包含**：新增智能体、删除/重命名会话、自动标题、流式输出、文件/图片消息、后端接口或数据库扩展。
- **预期效果**：无需改变侧栏五个主入口及顺序，用户可完成新对话和历史续聊；刷新已有会话地址后仍能查看对应消息。

## 2. 已确认需求与澄清结果

| 事项 | 确认结果 | 方案影响 |
|---|---|---|
| “我的智能体” | 按截图落地卡片入口 | 替换 `/agents` 占位内容，不复用“技能市场”的演示卡片数据 |
| 对话 | 点击卡片进入独立对话页 | 新增对话路由；使用现有完整 JSON 响应，不设计流式展示 |
| 历史 | 对话页可切换，侧栏“会话记录”可打开并继续 | `/sessions` 替换占位内容；两个位置复用同一历史列表组件 |
| 添加控件 | 显示为明确未开放状态 | 保留截图中的两个位置，不产生添加请求或误导性的可点击反馈 |

使用者为已登录用户；输入为纯文本或当前题卡的选项；输出为完整回答或下一张题卡。后端按当前用户限制会话范围。空白输入不提交、提交期间防重复提交；请求失败要显示反馈且不自动重发。其余需求与验收条件以需求文档为准。

## 4. 设计与职责

### 路由和页面

- 保留 `/agents` 为卡片入口、`/sessions` 为历史列表。新增**内部页面路径** `/chat`（空白对话）与 `/chat/:conversationId`（已有会话）；它们不是主导航项。路径解析只接受十进制字符串 ID，保留浏览器前进后退及直达地址能力。
- `/chat` 显示可输入的空白视图，不在点击卡片时创建空会话。第一次有效发送时先创建会话，再进入 `/chat/:conversationId` 并发送文本。已有会话直接读取消息并继续。
- 顶栏沿用 `PlatformLayout`；对话页归属“我的智能体”上下文，历史页归属“会话记录”。新页面不改侧栏顺序、全局导航或其他占位页。

### 前端业务与数据流

```text
我的智能体卡片 -> /chat -> 首次发送 -> POST /api/conversations -> /chat/:id
                                                -> POST /api/conversations/{id}/messages
对话页历史列表 / /sessions -> GET /api/conversations -> 选中 ID
                            -> GET /api/conversations/{id}/messages -> /chat/:id
待答题卡 -> POST /api/conversations/{id}/answers -> 刷新当前消息
```

- `conversationApi.ts` 只负责类型化的会话请求、Cookie、错误解析和字符串 ID，不混入页面状态；现有 `authApi.ts` 的认证行为不变。请求通过同源 `/api` 地址，沿用浏览器 Cookie；写入接口遵守现有 Origin 检查。
- 对话页面持有当前会话、消息、输入、题卡选择和提交状态；历史列表组件接收会话数据与选中回调，供对话页和 `/sessions` 复用。会话无标题时以创建时间等现有字段显示稳定的“未命名会话”标签，不编造自动标题。
- 发送成功后以消息接口刷新当前会话，使用户消息和助手响应均以服务端持久化结果为准。若发送返回失败，保留输入并刷新当前消息，显示错误且不自动重试；因为服务端可能已保存用户消息。题卡提交遵循相同原则。
- 消息接口按 ID 升序且最多 100 条/页。对话页分页读取直至当前会话末尾，以正确识别最后一条是否为待答题卡；在长会话中显示加载进度或延迟提示，避免误认已加载完整。历史列表同样按现有 `limit`/`offset` 分页，并提供继续加载入口。
- 题卡按返回的 `question` part 展示 1–3 道单选题；用户完成每题选择后提交 `question ID -> option label` 映射。待答期间禁用普通文本提交。刷新或切换回来时根据最新持久化消息恢复待答状态。
- 访问无权会话与不存在会话均按现有 404 契约提示；401 引导重新登录；409/422/503 显示明确反馈。动态状态使用可访问文字提示，控件保留键盘焦点与禁用语义。

本方案只新增前端业务模块。无需引入路由、状态管理或 UI 框架；当前 `App.tsx` 的 History API 导航模式足以承载新增地址。

## 7. 接口与数据库影响审查

### 接口影响：**无后端接口变更**

| 方法与路径 | 操作 | 当前定义 | 复用的契约与兼容性 |
|---|---|---|---|
| `POST /api/conversations` | 保持不变 | `backend/app/modules/conversations/router.py` | 首次发送前创建空会话；返回字符串 ID，现有调用方不受影响 |
| `GET /api/conversations` | 保持不变 | 同上 | 当前用户会话按更新时间倒序分页；前端使用现有 `limit`/`offset` |
| `GET /api/conversations/{id}/messages` | 保持不变 | 同上 | 按 ID 升序分页读取当前用户消息；前端按 `parts` 展示文本或题卡 |
| `POST /api/conversations/{id}/messages` | 保持不变 | 同上 | 接收非空文本，返回 `completed` 或 `waiting` 及助手消息；前端不依赖流式输出 |
| `POST /api/conversations/{id}/answers` | 保持不变 | 同上 | 提交题目 ID 与选项标签映射，继续原会话 |
| `GET /api/auth/session` | 保持不变 | `backend/app/modules/auth/router.py` | 继续由 `App.tsx` 恢复登录状态并保护页面 |

核查了 `router.py`、`schemas.py`、`service.py`、`docs/api/api.md`。新增的 `/chat` 和 `/chat/:id` 是**前端页面地址**，不是后端 API。当前接口足以对应全部已确认的用户操作；不为页面展示新增端点。长会话需要逐页读取消息，是现有升序分页契约的性能风险，见第 10 节。

### 数据库影响：**无数据库变更**

| 表 / 字段 | 操作 | 当前定义 | 用途 | 迁移、回填与回滚 |
|---|---|---|---|---|
| `conversations.id`, `user_id`, `title`, `created_at`, `updated_at` | 保持不变 | `backend/app/modules/conversations/models.py`、迁移 `0003`/`0004` | 归属、历史排序、字符串 ID 与无标题展示 | 无迁移、回填或数据库回滚 |
| `messages.id`, `conversation_id`, `role`, `content`, `created_at` | 保持不变 | 同上 | 多轮文本、题卡、历史展示 | 无迁移、回填或数据库回滚 |

现有 `content.parts` 已承载文本和题卡；现有 `title` 可为空。页面不要求额外字段或索引。最小变更是新增前端页面、API 客户端与测试；排除新表、自动标题和重复的对话 API。没有尚待确认的接口或数据决策。

## 10. 假设、风险与运行考虑

- **非阻塞假设**：遵循已确认需求中的空白对话假设；首条有效消息到来时才创建会话。无标题会话以固定“未命名会话”加现有时间信息标识，不生成或保存新标题。
- **长会话性能**：现有消息列表按升序分页且没有总数/倒序查询。为恢复最新待答状态需逐页读至末尾；首版沿用现有接口并提供加载反馈。若生产数据量证明该方式不足，再单独评估接口优化，不在本次预增端点。
- **请求失败后的状态**：后端先保存用户消息再调用模型；503 不保证未写入。因此失败后重新读取消息，不自动重发，避免用户无感知地产生重复消息。
- **安全与隐私**：继续使用 Cookie 和服务端所有权校验；前端不传 `user_id`，不记录消息正文到日志或浏览器持久存储。Snowflake ID 始终按字符串处理。
- **兼容与发布**：无数据库迁移和后端部署变化。前端可按原部署方式发布；回退前端版本即可移除入口，新产生的会话数据仍由现有后端保留。
