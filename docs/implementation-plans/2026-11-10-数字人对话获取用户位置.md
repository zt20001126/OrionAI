# 数字人对话中获取用户位置实现方案

> 日期：2026-11-10（Asia/Shanghai）  
> 状态：已按方案实现（检查结果见交付说明）  
> 需求确认：含已标注的非阻塞假设

## 1. 目标与背景

- **要解决的问题：** 数字人现有 `get_user_location` 工具通过请求 IP 查询省市，无法获取用户设备经纬度，不能满足附近商家推荐需求。
- **功能目标：** 用户在数字人对话中同意提供位置后，由浏览器请求定位权限并获取经纬度；数字人本轮 Agent 可读取该位置。
- **预期最终效果：** 数字人先在对话中说明用途并征求同意；用户通过数字人现有位置授权问答回复后，浏览器显示原生定位提示。允许后坐标仅随本轮请求传给后端；拒绝或失败时数字人询问区县、商圈或地址。

## 2. 已确认需求

- **使用者 / 调用方：** OrionAI 数字人对话用户及 `digital_human` Agent。
- **触发方式：** 用户提出附近商家等需要当前位置的请求，Agent 发起位置授权问答。
- **输入：** 用户授权问答结果；浏览器获取的经纬度和精度（成功时）。
- **输出：** 当前轮数字人 Agent 可使用的位置上下文；后续可由地点搜索能力查询 POI。
- **主流程：** 数字人按当前位置能力规则先征求授权 → 用户在对话问答中同意 → 前端调用浏览器 Geolocation → 坐标随问答请求发送 → 后端校验并注入本轮数字人配置 → 现有 `get_user_location` 工具读取坐标供数字人继续回答。
- **业务规则与边界：** 定位仅在用户明确同意后发起；不使用 IP 结果伪装成精确位置；坐标仅作为本轮内存上下文，不写入消息或用户资料。
- **异常行为：** 用户拒绝、浏览器不支持、超时或定位失败时不发送坐标，Agent 转为询问用户选择区县、商圈或输入地址。
- **权限与数据范围：** 浏览器定位需安全上下文（HTTPS，localhost 开发例外）及用户授权；服务器不能代替用户授予浏览器权限。
- **约束：** 不新增对话外的“定位”按钮，不在用户未同意时请求定位。

## 3. 范围

- **本次包含：** `digital_human` 的位置授权问答；浏览器坐标获取；本轮位置上下文传递；修改数字人现有位置工具以读取坐标；定位失败退路。
- **本次不包含：** 高德周边搜索和商家推荐的完整实现；WGS-84 到 GCJ-02 坐标转换；位置历史、持久化或用户画像。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| 对话前端 | 在数字人授权问答提交时请求浏览器位置；将坐标附加到问答请求 | 浏览器 API → 对话 API，不直接访问高德 |
| 对话 DTO / Router | 校验可选坐标并接收请求 | API 边界，不包含定位业务逻辑 |
| ConversationService | 仅在数字人问答明确允许后注入本轮位置上下文 | Router → Service → DigitalHumanRuntime；不持久化坐标 |
| 数字人 capability 与 `get_user_location` | 先征求同意；提供设备经纬度或说明 IP 粗略城市结果 | 复用数字人动态能力规则与既有定位工具 |

### 关键流程

```text
用户提出附近推荐或询问当前位置
  → 数字人通过现有题卡询问是否允许获取精确当前位置
  → 用户选择允许并提交
  → 前端 navigator.geolocation.getCurrentPosition
  → POST /api/conversations/{conversation_id}/runs/answers（附题卡答案和可选坐标）
  → DTO 校验 → ConversationService 当前轮配置 → DigitalHumanRuntime 恢复
  → get_user_location 读取坐标并返回数字人
```

浏览器权限弹窗必须由页面 Geolocation API 调用触发；它与用户在 OrionAI 内表达同意是两层确认。Geolocation 在 HTTPS 或 localhost 环境工作。拒绝、不可用或超时不应阻止题卡答案提交，后端收到无坐标的授权结果后让 Agent 采用地址/区县后备流程。

## 9. 接口与数据库变更审查

### 接口影响

| 接口（方法 + 路径 / 事件） | 操作 | 当前定义位置 | 变更前后契约 | 复用判断与变更理由 | 兼容性 / 调用方影响 |
|---|---|---|---|---|---|
| POST `/api/conversations/{conversation_id}/runs/answers` | 修改（可选字段） | `backend/app/modules/conversations/router/router.py` | 原有 `{answers}` 增加可选 `location` 对象，含授权结果及成功时的纬度、经度、精度 | 复用当前后台题卡恢复端点；前端通过它启动 Agent run | 字段可选，旧客户端继续可用；新前端仅在数字人位置授权问答时传入 |
| `navigator.geolocation.getCurrentPosition` | 新增前端调用 | `frontend/src/features/conversations/ConversationPage.tsx` | 用户明确同意后取得设备坐标；拒绝/失败以状态表达，不构造坐标 | 这是浏览器获取设备位置的标准接口 | 需 HTTPS 或 localhost；用户可拒绝 |

### 数据库影响

**无数据库变更。** `messages.content` 虽可保存 JSONB parts，本方案不将坐标写入会话消息、用户资料或其他表，仅在当前请求和 Agent 运行配置中短暂传递；不需要迁移或回填。

### 最小变更结论

- **可复用的现有接口 / 数据结构：** 数字人已有 `get_user_location`、capability 规则、题卡问答、后台问答 run 端点和本轮 Agent configurable。
- **本方案实际新增或修改的最小集合：** 对话端问答定位调用、请求 DTO 扩展、Service 临时上下文注入、数字人已有位置工具及能力规则。
- **排除的冗余设计及原因：** 不添加定位按钮、独立授权 API、坐标数据库字段；当前一轮问答恢复机制可承载授权与坐标输入。
- **尚未确认的接口或数据决策：** 首期坐标按浏览器提供的 WGS-84 保存于本轮内存；高德 POI 搜索及其坐标系转换留作后续阶段。

## 10. 分步实施计划

### 步骤 1：定义位置授权问答与浏览器定位交互

- **目的：** 用户通过现有对话问答表达允许/拒绝，允许时触发系统定位授权。
- **涉及文件：** `ConversationPage.tsx`、`conversationApi.ts`、`ConversationPage.test.tsx`（新增）。
- **实施内容：** 对指定位置授权题卡在提交时调用 Geolocation；使用 HTTPS 浏览器环境；配置超时和缓存年龄；将拒绝、不支持、超时转为明确状态；普通题卡流程不变。
- **前置依赖：** 无。
- **验收标准：**
  - [ ] 用户拒绝 OrionAI 内授权时，浏览器定位 API 不被调用。
  - [ ] 用户同意后，浏览器收到定位请求；成功结果包含纬度、经度和精度。
  - [ ] 浏览器拒绝或定位失败时，问答仍可提交且不包含虚构坐标。
- **验证方式：** 前端组件测试 mock Geolocation；浏览器 HTTPS 环境手工验证授权、拒绝和超时。

### 步骤 2：扩展问答 API 并传递本轮位置上下文

- **目的：** 将坐标安全地从浏览器传到当前 Agent 运行。
- **涉及文件：** `conversationApi.ts`、`backend/app/modules/conversations/schemas/schemas.py`、`router/router.py`、`service/service.py`、`conversationApi.test.ts`、`backend/tests/unit/test_conversation_stream_config.py`、`backend/tests/integration/test_conversation_endpoints.py`。
- **实施内容：** 请求增加可选位置状态与坐标；后端校验坐标范围和授权状态；允许时将坐标只放入当前轮 `configurable`；无坐标或拒绝时只传状态；消息内容仅保存题卡答案。
- **前置依赖：** 步骤 1。
- **验收标准：**
  - [ ] 合法且明确授权的坐标到达本轮 Agent 配置。
  - [ ] 未授权状态带坐标或越界坐标被 API 拒绝。
  - [ ] 从消息历史读取的内容不包含经纬度。
  - [ ] 不传新字段的现有客户端请求仍通过原契约。
- **验证方式：** API schema 和 Service 单元/集成测试，检查 Agent 收到的配置及数据库消息内容。

### 步骤 3：让数字人位置工具使用授权坐标

- **目的：** 使数字人只在授权后使用本轮位置，失败后能询问用户替代位置。
- **涉及文件：** `backend/app/modules/digital_human/agent/capabilities.py`、`backend/app/modules/digital_human/agent/tools/location.py`、数字人位置和 Agent 测试。
- **实施内容：** 复用数字人 `get_user_location` 读取当前运行配置中的已授权坐标；更新位置能力规则，精确定位和附近搜索前先征求许可；定位失败时询问区县、商圈或地址；单纯城市查询保留并说明 IP 粗定位限制。
- **前置依赖：** 步骤 2。
- **验收标准：**
  - [ ] 数字人仅在位置授权题卡选择允许且坐标可用时读取设备坐标。
  - [ ] 用户拒绝或浏览器失败时，附近搜索场景询问替代地址；城市定位仍可使用并标注为 IP 粗定位。
  - [ ] 不影响数字人已有题卡、语音、提醒、简历和其他工具调用。
- **验证方式：** 数字人位置工具单元测试及数字人 Agent 工具注册/运行测试。

## 12. 风险、假设与运行考虑

- **非阻塞假设：** 本次只改数字人智能体；商家 POI 搜索将在其拿到坐标后作为下一阶段，不在本方案中新增高德周边搜索工具。
- **主要风险及应对：** 浏览器位置权限提示受浏览器、站点权限、iframe 策略和安全上下文影响；前端须提供失败状态，后端不得假设坐标一定存在。
- **安全 / 隐私 / 性能 / 可观测性：** 明确说明用于附近商家推荐；仅接受授权后的坐标；不落库、不写入日志、不传给无关 Agent；限制合法经纬度范围。
- **发布、迁移或回滚：** 无数据库迁移；可通过回滚前后端代码恢复旧问答契约，新增字段为可选。
