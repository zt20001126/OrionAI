# 数字人提醒创建工具实现方案

> 历史设计记录：本文反映编写时的需求或方案，可能与当前实现不同；当前行为请查阅 [README](../../README.md)、[架构概览](../architecture/overview.md)及源码。

> 日期：2026-11-06（Asia/Shanghai）
> 状态：已实施
> 需求确认：已澄清

## 1. 目标与背景

- **要解决的问题：** 用户目前不能在数字人对话中直接安排提醒。
- **功能目标：** 为数字人增加创建提醒能力，复用提醒模块现有校验、计划计算、数据库事务和后台调度。
- **预期最终效果：** 数字人通过 `get_current_date` 获取北京时间，收集并复述提醒信息，以题卡等待用户确认；用户确认后创建提醒，用户取消则不写入提醒表。

## 2. 已确认需求

- **使用者 / 调用方：** 当前会话中的登录用户，通过 `digital_human` 智能体使用。
- **触发方式：** 用户明确要求数字人设置提醒。
- **输入：** 标题、提醒内容、重复类型、日期或开始日期、本地时间、时区及可选结束日期。相对日期先调用数字人现有 `get_current_date` 获取北京时间再换算。
- **输出：** 创建成功时告知用户提醒已创建及其时间规则；取消时告知未创建；失败时说明未能创建，不声称成功。
- **主流程：**
  1. 数字人识别提醒意图，调用 `get_current_date` 获取北京时间。
  2. 通过自然语言对话或现有题卡补齐创建所需字段；对不明确的日期、时间或重复规则进行澄清。
  3. 调用提醒准备工具校验并规范化字段，生成包含完整提醒信息的确认题卡，将待确认草稿短期保存。
  4. 数字人图将有效确认题卡作为等待用户输入的题卡返回。
  5. 用户确认后，会话服务校验并原子领取草稿，调用提醒应用服务创建；取消或草稿过期时不创建。
  6. 数字人依据系统提供的创建结果答复；已创建提醒由既有 Celery Beat/Worker 流程调度发送。
- **业务规则与边界：**
  - 单次提醒使用 `date`；周期提醒使用 `start_date`；时间字段为 `local_time`，格式 `HH:MM`。
  - `repeat_type` 取 `once`、`daily`、`weekly`、`monthly`。当前提醒 schema 将每周日期设为开始日期对应的星期，将每月日期设为开始日期的日号；本需求不新增自定义多星期规则。
  - 默认时区为 `Asia/Shanghai`，与现有日期工具的北京时间语义一致。用户明确提供其他时区时使用其有效 IANA 时区；相对日期以其确认的时区解释。
  - 创建服务要求首次计划严格晚于服务器当前时间；过期或 DST 不存在/歧义的单次本地时间由现有业务校验拒绝。
  - 用户 ID 从可信的 RunnableConfig 会话上下文取得，不接受模型参数指定用户或邮箱。
  - 用户确认前不创建数据库提醒；重复提交同一确认不得重复创建。
- **异常行为：** 参数校验错误、数据库错误、草稿过期及重复确认均返回清晰结果；不得吞错或伪报创建成功。
- **权限与数据范围：** 仅为发起该数字人会话的当前用户创建提醒。提醒邮箱沿用账号邮箱，由提醒执行服务读取。
- **约束：** 不直接写 SQL，不修改提醒调度流程，不新增提醒业务表或公共 API。

## 3. 范围

- **本次包含：** 数字人工具注册、能力提示词、确认题卡/草稿、会话确认处理、复用 `ReminderService` 创建、单元及集成验证。
- **本次不包含：** 提醒编辑/暂停/取消/查询工具；提醒 API 或 UI 变更；多星期或更复杂重复表达；更改数字人导航或邮件工具行为。日期工具仅增加可选 IANA 时区参数，保持无参数时原有北京时间输出。

## 6. 架构设计

### 模块职责与边界

| 模块 | 职责 | 依赖方向 / 边界 |
|---|---|---|
| 数字人提醒准备工具（拟新增） | 校验工具输入、生成确认题卡、按可信用户/会话上下文存储草稿 | 依赖提醒 DTO、题卡 schema 和 Redis；不直接写业务表。 |
| 数字人图与能力描述 | 注册工具并让模型知道何时调用、如何补齐及确认 | 依赖数字人工具；保持图只负责编排。 |
| 会话服务 | 校验用户提交的确认答案，领取匹配草稿，并在确认后调用提醒 Service | 通过 ReminderService 进入提醒业务层，不执行 SQL 业务逻辑。 |
| ReminderService | 校验和创建提醒、计算下次计划、提交事务 | 既有业务模块，保持为 reminders 表的写入入口。 |
| Celery 扫描与执行 | 按既有方式产生执行记录并发送邮件 | 无需变更。 |

### 关键流程

```text
用户请求
  -> 数字人调用 get_current_date（相对日期时）
  -> 数字人收集/确认字段
  -> prepare_reminder（校验、Redis 草稿、确认题卡）
  -> 用户提交确认
  -> 会话服务领取草稿
  -> ReminderService.create（事务写 reminders）
  -> 现有 Celery 扫描、执行和邮件通知
```

确认前写数据库会带来用户未同意即创建的副作用，因此方案复用数字人邮件确认的题卡暂停协议。提醒工具仅准备并展示内容；唯一创建入口是用户确认后的 `ReminderService.create`。题卡草稿使用一次性领取，避免并发重复确认创建多条提醒。

### 最小变更结论

- **可复用的现有接口 / 数据结构：** `ReminderCreateRequest`、`ReminderService.create`、数字人 `get_current_date`、`ask_user_questions` 题卡协议及 Redis 确认草稿模式。
- **本方案实际新增或修改的最小集合：** 一个数字人提醒工具、数字人图/能力规则、会话服务确认分支及对应测试。
- **排除的冗余设计及原因：** 不新增提醒表、API、通用任务/outbox、Agent 通用工具注册机制，也不直接从工具运行 SQL。
- **尚未确认的接口或数据决策：** 无。用户明确采用确认题卡；默认时区为 `Asia/Shanghai`，并允许用户明确指定其它有效 IANA 时区。

## 10. 分步实施计划

### 步骤 1：实现提醒准备工具和确认草稿

- **目的：** 在确认前安全收集和展示提醒规则。
- **涉及文件：** `backend/app/modules/digital_human/agent/tools/reminder.py`（新增）；`backend/tests/unit/test_digital_human_reminder_tool.py`（新增）。
- **实施内容：** 使用严格 Pydantic schema 约束字段，复用 `ReminderCreateRequest` 的业务校验；用 `RunnableConfig` 可信上下文绑定当前用户和会话；将规范化 payload 写入有 TTL 的 Redis 草稿；生成展示完整日期、时间、重复和时区的确认/取消题卡。
- **前置依赖：** 无。
- **验收标准：**
  - [ ] 缺失字段、非法时区、错误日期/时间和互斥日期字段不会生成确认草稿。
  - [ ] 题卡内容与保存的规范化请求一致，草稿键包含用户、会话和唯一题卡 ID。
  - [ ] Redis 草稿设置有限 TTL；工具参数不能指定 user_id、状态或收件邮箱。
- **验证方式：** 工具单元测试使用 Redis 客户端替身检查校验和草稿读写参数。

### 步骤 2：注册数字人能力并让图等待确认

- **目的：** 让模型发现提醒能力，并通过现有题卡协议等待用户选择。
- **涉及文件：** `backend/app/modules/digital_human/agent/graph.py`、`backend/app/modules/digital_human/agent/capabilities.py`、`backend/app/modules/digital_human/agent/tools/__init__.py`；数字人图测试文件。
- **实施内容：** 注册新工具；扩展有效提醒题卡名称转换，使其等同 `ask_user_questions` 触发 pause；在能力规则中指导模型相对日期先调用 `get_current_date`，信息不足先询问，展示完整计划后调用准备工具，并等待确认结果。
- **前置依赖：** 步骤 1。
- **验收标准：**
  - [ ] 数字人启动提示列出提醒能力及确认规则；未注册工具不会出现在能力列表。
  - [ ] 有效提醒确认题卡暂停数字人图，用户回复后图可继续；普通工具结果仍回到模型。
  - [ ] 工具名称保持符合 `ToolRegistry` 的小写下划线约束。
- **验证方式：** 数字人图单元测试检查注册集合、提示词能力和题卡路由。

### 步骤 3：在确认答案中创建提醒

- **目的：** 仅在用户确认后提交提醒写入。
- **涉及文件：** `backend/app/modules/conversations/service/service.py`；`backend/tests/unit/test_conversation_service_reminder_confirmation.py`（新增）。
- **实施内容：** 通过提醒题卡 ID 前缀识别确认题卡；核对题卡展示内容和草稿绑定关系；用 Redis 一次性领取草稿；若答案为确认，在会话用户上下文中构造 `ReminderCreateRequest` 并调用 `ReminderService.create`；取消、失效或重复答案不调用创建服务；把处理结果附加到恢复模型的消息中。
- **前置依赖：** 步骤 1、2。
- **验收标准：**
  - [ ] 确认答案最多触发一次当前用户的 ReminderService.create。
  - [ ] 取消、草稿缺失/过期、题卡与草稿内容不符均不创建提醒。
  - [ ] Service 校验或数据库异常不会返回“已创建”；不会泄露敏感信息。
  - [ ] 创建得到的 reminder ID/计划信息仅在必要范围提供给模型用于用户答复。
- **验证方式：** Service 单元测试模拟数据库会话、ReminderService 和 Redis 的确认/取消/失效/重复/失败路径。

### 步骤 4：端到端回归数字人提醒流程

- **目的：** 验证完整确认交互与现有调度兼容。
- **涉及文件：** 相关数字人及会话测试；必要时新增集成测试。
- **实施内容：** 覆盖自然日期转换所需的日期工具调用、确认题卡暂停和答案恢复；确认创建的记录由现有提醒调度器识别。
- **前置依赖：** 步骤 1–3。
- **验收标准：**
  - [ ] 用户说“明天上午九点提醒我……”时模型先取得北京时间日期，生成明确的日期与时间并展示确认题卡。
  - [ ] 用户确认后产生一条归属当前用户、`status=active` 且未来 `next_run_at` 正确的提醒记录。
  - [ ] 用户取消时提醒表无新增记录；创建的提醒可被现有扫描器按计划识别。
- **验证方式：** 对话/服务集成测试验证题卡生命周期和提醒记录；调度器测试验证到期扫描兼容。运行实施时按项目流程执行相关测试与静态检查。

## 12. 风险、假设与运行考虑

- **非阻塞假设：** 提醒发送继续使用账号邮箱和既有 SMTP 配置；用户可用工具准备之外的对话表达重复规则，但最终都必须映射到当前支持的 once/daily/weekly/monthly 字段。
- **主要风险及应对：** 模型可能把相对时间转换错误，因此确认题卡必须展示明确日期、时间和时区；`ReminderService` 再校验首个计划晚于当前时刻。草稿 TTL 到期后要求用户重新准备，不能尝试从题卡答案重建草稿。
- **安全 / 隐私 / 性能 / 可观测性：** 用户身份仅从可信运行上下文获取；草稿按用户/会话/题卡隔离、短期保留且一次性领取；日志不得记录提醒正文或邮箱。Redis 不可用时工具明确失败且不创建数据库数据。
- **发布、迁移或回滚：** 无数据库迁移；部署代码后数字人提示和工具生效。回滚时移除工具和确认处理逻辑，遗留草稿由 TTL 清理。
