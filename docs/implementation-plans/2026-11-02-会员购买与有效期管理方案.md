## 1. 目标与设计原则

在 OrionAI 现有模块化单体中增加一次性会员购买能力。用户通过 Stripe Checkout 沙盒付款；服务端通过验签 Webhook 确认付款后，按固定天数授予会员期限。已有期限未结束时，新购买期限排在最后一段期限后生效，套餐档位可以不同。

设计重点：

- 业务规则归会员模块；支付提供商协议归支付模块和基础设施适配器。
- 订单保存成交金额和期限快照，套餐后续变化不改写已创建订单。
- Webhook 是支付成功的唯一可信来源；浏览器回跳仅用于展示和查询。
- 三张业务表表达套餐、订单、会员期限；不改 users 表，不增加通用支付表、权益表或缓存。
- 接口、状态和数据约束在实现前明确，便于后续评审、实现和测试。

## 2. 已确认需求与首期边界

| 项目 | 已确认方案 |
|---|---|
| 购买方式 | 一次性固定期限，不自动续费 |
| 支付渠道 | 沿用 Stripe Checkout；首期仅沙盒 |
| 套餐档位 | 月度 9.90 元/30 天、季度 99.90 元/90 天、年度 999.90 元/365 天 |
| 币种 | 首期固定 CNY；不做多币种报价 |
| 档位权益 | 三个档位权益相同，只区分名称、价格和有效天数 |
| 会员期限 | 统一按固定天数计算；所有业务时间存 UTC |
| 重复购买 | 新期限接在用户当前或已排期的最后一个期限后；购买不同档位也顺延 |
| 套餐维护 | 首期通过迁移或后台数据维护；前端只读启用套餐；不做管理界面/API |
| 首期会员能力 | 完成购买、续期和会员状态查询；不改造 AI 功能访问权限 |
| 首期不做 | 自动续费、退款、争议处理、权益/额度/角色、多支付渠道、完整订单历史列表 |

套餐价格来自本次需求材料，不能在支付代码中写成客户端可控值。若上线前价格发生调整，应通过套餐数据维护流程更新，并保留已创建订单的金额快照。

## 3. 领域规则与状态

### 3.1 购买和期限

1. 套餐列表只返回启用套餐。公开只读套餐目录；访客可以浏览，但不能创建订单或读取个人会员信息。
2. 创建订单时，后端先按可信 user_id 和 request_id 查找既有请求；同键同 plan_id 直接返回原订单，即使套餐后来停用也不影响该订单。只有新请求才校验套餐启用状态，并读取当前价格和有效天数写入订单快照。请求体不接受 user_id、价格、币种或有效天数。
3. 已创建的待支付订单不因套餐被停用或调价而改变；套餐停用只影响新订单。
4. 成功付款确认时间记为服务端验证并处理付款事件的 UTC 时间。
5. 新期限开始时间为 max(付款确认时间, 该用户已有会员期限的最大 expires_at)；结束时间为开始时间加订单快照 duration_days 天。
6. 期限采用左闭右开区间 [starts_at, expires_at)，避免到期边界重叠。
7. 订单状态和会员期限在同一个数据库事务内提交；事务失败时不留下部分入账。
8. 一笔成功订单最多关联一段会员期限。重复 Webhook 不增加第二段期限。

### 3.2 订单状态

允许的持久化状态：pending、paid、failed、expired。

- pending：订单已创建，尚未确认付款。
- paid：通过签名验证并完成金额、币种、订单关联核对的 Stripe 事件确认付款；状态不可降级。
- failed：Stripe 已确认该订单支付无法完成，且该 Checkout Session 不会再成功结算。
- expired：Checkout Session 过期且未付款。
- 未收到可信事件时保持 pending。客户端关闭页面、支付页跳转失败或浏览器报告成功都不改变订单状态。
- 对已 paid 订单收到失败、过期或重复事件，不得覆盖 paid 状态。
- Webhook 事件无法匹配本地订单或校验不通过时不发放会员期限；可记录受控错误和关联 ID，不记录敏感支付载荷。

## 4. 数据库设计

只新增三张业务表：membership_plans、membership_orders、memberships。复用现有 users 表和 Snowflake 主键约定，不给 users 增加会员字段。

### 4.1 membership_plans：可售套餐

| 字段 | 类型 | 约束/用途 |
|---|---|---|
| id | BIGINT | Snowflake 主键 |
| name | VARCHAR(100) | 套餐名；唯一，用作首期种子数据的稳定自然键 |
| price | NUMERIC(10,2) | CNY 售价；CHECK price > 0；应用层使用 Decimal |
| duration_days | INTEGER | 固定有效天数；CHECK duration_days > 0 |
| is_enabled | BOOLEAN | 是否接受新订单；默认 true |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

精简说明：

- 不保留 code、currency、权益 JSON、软删除标志或多币种价格表。首期只有 CNY，code 也不是对外必需输入；接口使用 plan_id。
- name 同时用于展示和种子数据冲突匹配。已被订单引用的套餐不物理删除；套餐改名需通过明确的数据迁移，并同步种子策略。
- 金额字段在 PostgreSQL 使用 NUMERIC(10,2)，SQLAlchemy 映射 Decimal；禁止使用 float。API 以两位小数字符串返回，如 "9.90"。
- Stripe 请求金额使用 Decimal 精确换算成最小货币单位整数（CNY 元乘 100）。

### 4.2 membership_orders：购买及支付记录

| 字段 | 类型 | 约束/用途 |
|---|---|---|
| id | BIGINT | Snowflake 主键 |
| user_id | BIGINT | FK users.id；只由认证上下文写入 |
| plan_id | BIGINT | FK membership_plans.id；引用下单时选择的套餐 |
| amount | NUMERIC(10,2) | 成交金额快照；CHECK amount > 0 |
| duration_days | INTEGER | 成交期限快照；CHECK duration_days > 0 |
| request_id | VARCHAR(36) | 客户端 UUID 幂等键 |
| stripe_session_id | VARCHAR(255) NULL | Stripe Checkout Session ID；唯一索引，可空 |
| status | VARCHAR(16) | pending/paid/failed/expired；CHECK 限定 |
| paid_at | TIMESTAMPTZ NULL | 服务端确认付款时间 |
| created_at | TIMESTAMPTZ | 创建时间 |
| updated_at | TIMESTAMPTZ | 更新时间 |

约束与索引：

- UNIQUE(user_id, request_id)：同一用户同一请求键只对应一个订单。
- UNIQUE(stripe_session_id)：一个 Stripe Session 不能绑定多个订单；NULL 允许尚未创建 Checkout 的订单。
- UNIQUE(id, user_id)：供会员期限表使用复合外键，保证期限的 user_id 与订单所有者一致。
- 索引 (user_id, created_at)：支持本人订单查询和排期读取。
- user_id、plan_id 外键删除策略采用 RESTRICT；交易数据不随用户或套餐删除而级联消失。
- 不保存套餐名称快照。名称通过 plan_id 关联；首期套餐名稳定且只允许停用不删除。成交金额和有效天数必须保留快照，因为它们决定实际扣款和授予期限。
- request_id 仅用于订单创建幂等。相同键、相同 plan_id 返回原订单；相同键、不同 plan_id 返回 409。订单过期或失败后，用户应使用新 request_id 创建新订单。

### 4.3 memberships：已购买期限

| 字段 | 类型 | 约束/用途 |
|---|---|---|
| order_id | BIGINT | 主键，同时 FK membership_orders(id, user_id) 的一部分；每笔订单最多一个期限 |
| user_id | BIGINT | FK users.id，并与订单所有者通过复合外键校验 |
| starts_at | TIMESTAMPTZ | 期限开始时间 |
| expires_at | TIMESTAMPTZ | 期限结束时间；CHECK expires_at > starts_at |

约束与查询：

- 复合外键 (order_id, user_id) -> membership_orders(id, user_id)，避免会员期限挂到另一个用户名下。
- UNIQUE(order_id) 由主键保证；索引 (user_id, starts_at, expires_at) 支持当前和未来期限查询。
- PostgreSQL 使用半开区间做同用户期限不重叠约束。建议通过 btree_gist 扩展创建 EXCLUDE 约束：同一个 user_id 的 tstzrange(starts_at, expires_at, '[)') 不允许重叠。迁移启用扩展但 downgrade 不删除共享扩展。
- 即使数据库有排斥约束，Service 仍需锁定 users 对应行后计算最大 expires_at；数据库约束是并发异常和遗漏写入的最后防线。
- 不存会员状态、套餐 ID或单独的会员记录 ID：状态由当前时间与期限范围计算；套餐从 order.plan_id 查询；order_id 已是唯一身份。

### 4.4 三表关系

- 一个 membership_plan 可以关联多笔 membership_orders。
- 一个 users 用户可以关联多笔 membership_orders 和 memberships。
- 一个 membership_order 最多关联一段 membership。
- 当前会员期限满足 starts_at <= now < expires_at；未来期限 starts_at > now；已过期期限 expires_at <= now。
- 当前会员接口返回 active_period（没有则 null）和 upcoming_periods（按 starts_at 升序）。不维护重复的用户会员快照。

### 4.5 种子数据与迁移

- Alembic 新迁移接续当前 head 0016_guest_users，目标版本为 0017_membership_billing。
- 在迁移中种入三档：月度会员 9.90/30 天、季度会员 99.90/90 天、年度会员 999.90/365 天，均启用。
- 种子不使用硬编码 Snowflake ID，也不在每次应用启动时写入套餐。按现有迁移约定使用 migration 专用 Snowflake worker（worker 1023）生成 ID；生成器逻辑在迁移中冻结，不依赖运行时应用实例。
- 用 UNIQUE(name) 配合 INSERT ... ON CONFLICT(name) DO NOTHING 实现重复执行安全，并保留后台调整过的启用状态。后续改价或有效天数应由新的明确迁移/数据维护操作完成，不靠应用启动覆盖。
- downgrade 删除本次创建的业务表和约束；不自动删除 btree_gist 扩展。上线后如已有交易或期限，回滚前须先备份并由运维决定是否允许删除相关业务数据。
- 不修改 users 表，不需要历史数据回填。

## 5. Stripe Session 字段删减审查

需求要求评估是否删除 stripe_session_id 和 checkout_url。结论：

- checkout_url 不入库。创建成功后把 URL 返回给用户；重复查询时根据已保存的 stripe_session_id 调用 Stripe Retrieve 获取当前 Checkout URL。URL 是可重新读取的临时展示信息，不是业务事实。
- stripe_session_id 保留为 membership_orders 的唯一可空字段，这是实现可靠回调关联所需的最小支付提供商标识。Webhook 必须能把已验签的 Session 与本地订单一对一匹配；它也支持用户重试取回现有 Session、避免同一订单创建多个可付款 Session。
- 仅使用 Stripe Idempotency-Key 不足以代替持久化 Session ID。Stripe API v1 的幂等结果可能在至少 24 小时后被清理；Checkout Session 默认有效 24 小时，允许配置的有效期在 30 分钟至 24 小时之间。若不持久化 Session ID，稍后重试难以确认原 Session，可能创建第二个可付款会话。
- Checkout Session 创建使用订单级稳定 Idempotency-Key；Stripe 返回 Session 后，将 session_id 写入订单。Checkout Session 创建和数据库提交无法组成一个分布式事务，因此重试应先检查本地 session_id，再用相同 Idempotency-Key恢复 Stripe 响应。Session 过期后不复用旧订单创建新 Session，用户需新建订单。
- Webhook 至少校验签名、livemode=false、mode=payment、session_id 与订单匹配、metadata/client_reference_id 中的订单关联、币种为 CNY、总额与订单 amount 快照一致、payment_status=paid。未满足全部条件不入账。
- 以此对用户提出的字段删减做最小修正：删除 checkout_url；保留 stripe_session_id，并明确它是关联与幂等恢复所需的最小持久化字段。

Stripe 依据：

- [Stripe Idempotent requests](https://docs.stripe.com/api/idempotent_requests)：幂等请求的结果会被保存，但 API v1 的键可能在至少 24 小时后清理。
- [Create a Checkout Session](https://docs.stripe.com/api/checkout/sessions/create)：Checkout Session 返回 id 和 url；Session 过期时间默认 24 小时，可配置范围为 30 分钟至 24 小时。
- [Retrieve a Checkout Session](https://docs.stripe.com/api/checkout/sessions/retrieve)：可根据 Session ID 重新读取 Session，包括 URL。

## 6. 模块与依赖边界

| 模块 | 负责内容 | 不负责内容 |
|---|---|---|
| backend/app/modules/membership/ | 套餐、订单、会员期限模型与持久化；套餐可售校验；请求幂等；金额/天数快照；订单状态规则；期限排期；事务与用户数据归属 | Stripe SDK、Webhook 签名细节、Checkout URL 生成 |
| backend/app/modules/payment/ | Stripe Checkout 用例；Webhook 接收和事件流程；调用会员应用服务读取订单支付上下文、登记 Session ID、确认成功/失败/过期结果 | 会员期限计算、直接操作会员 ORM 或自行发放会员 |
| backend/app/infrastructure/payments/ | Stripe SDK 封装；创建/查询 Checkout Session；原始请求签名验证；Stripe 对象转换为内部支付事件 | 会员订单状态规则、数据库访问 |
| Router | HTTP 参数、认证/来源校验、调用 Service、组织响应 | 事务、金额计算、Stripe SDK 调用 |
| Service | 应用用例及领域规则编排 | 直接解析 HTTP 或持有 provider SDK 细节 |
| Repository | SQLAlchemy 查询、写入、锁行和事务数据访问 | HTTP 状态码、Stripe 协议 |

依赖方向：payment -> membership 应用服务；payment -> infrastructure Stripe adapter。membership 不依赖 payment，infrastructure 不依赖业务模块。会员 Service 不创建 Stripe Session；支付成功后由 payment 服务把已核验的标准化事件交给 membership 服务完成原子入账。这样可避免模块循环依赖及一处 Service 承担两种业务职责。

## 7. API 契约

应用现有 API 前缀为 /api。以下是完整路径。错误响应继续沿用项目统一异常处理约定；新增业务错误应接入现有错误映射。

### 7.1 套餐列表

GET /api/v1/membership/plans

- 认证：公开只读；不返回停用套餐。
- 请求：无。
- 响应：套餐数组，每项包含 id（十进制字符串）、name、price（两位小数字符串）、duration_days。
- 示例字段：id="..."，name="月度会员"，price="9.90"，duration_days=30。
- 不包含 currency 字段，因为首期固定 CNY；页面标题或接口文档明确价格单位为人民币元。
- 失败：数据库暂时不可用返回统一服务端错误；空套餐返回空数组。

### 7.2 创建会员订单

POST /api/v1/membership/orders

- 认证：RegisteredUser + Origin 来源校验；游客不能购买。
- 请求：plan_id（Snowflake 十进制字符串）、request_id（UUID 字符串）。
- 不接受 user_id、amount、price、duration_days、currency 或 Stripe 字段。
- 成功响应：order_id、status、amount、duration_days、created_at。
- 服务端以认证用户 ID、启用套餐和 request_id 创建订单；相同用户和请求键重试返回相同订单。
- 错误：未登录 401、游客 403、套餐不存在或已停用 404、相同 request_id 对应不同套餐 409、输入格式错误 422。

### 7.3 创建或重新获取 Checkout Session

POST /api/v1/payments/stripe/checkout-sessions

- 认证：RegisteredUser + Origin 来源校验。
- 请求：order_id。
- 成功响应：order_id、checkout_url、expires_at。
- 只允许订单所有者为 pending 的订单创建/读取 Session；请求用户和订单所有者必须一致，其他用户查询返回 404。
- 已绑定且未过期的 Session 从 Stripe Retrieve 返回 URL，不新建 Session；session_id 唯一，订单级 Idempotency-Key 保证重试稳定。
- 已付款、失败或过期订单不能重新创建 Checkout Session；过期后前端提示用户创建新订单。
- 不把 checkout_url 写入数据库，不接受客户端传入成功金额或回跳地址。

### 7.4 查询本人订单

GET /api/v1/membership/orders/{order_id}

- 认证：RegisteredUser。
- 响应：order_id、plan_id、status、amount、duration_days、created_at、paid_at。
- 无权限与不存在统一返回 404，避免泄漏其他用户订单。
- 这是回跳页轮询支付状态的依据。首期不提供分页历史订单列表。

### 7.5 查询本人会员期限

GET /api/v1/users/me/membership

- 认证：RegisteredUser。
- 响应：active_period（null 或 {plan_id, plan_name, starts_at, expires_at}）以及 upcoming_periods 数组（每项有 plan_id、plan_name、starts_at、expires_at）。
- 没有任何期限时返回 active_period=null、upcoming_periods=[]。
- 状态按服务端 UTC 当前时间计算；不改现有 /api/auth/session 或 AI API 权限。

### 7.6 Stripe Webhook

POST /api/payments/stripe/webhook

- 认证方式：Stripe-Signature 验签，不使用 Cookie、Origin 或用户身份。
- 读取未经修改的原始请求体；限制请求体大小；缺少/无效签名返回 400；临时数据库故障返回 5xx 供 Stripe 重试。
- 仅处理 Sandbox Checkout Session 相关成功、最终失败、过期事件；只为 payment_status=paid 且所有订单对账条件通过的事件授予期限。
- 已验签但不支持、重复或无法与本地订单匹配的事件，记录受控错误后返回 2xx，避免无效事件持续重试；数据库等临时故障返回 5xx。不能因重复投递反复创建会员期限。
- Webhook 不能信任前端 success_url、查询参数或前端报告的支付状态。

### 7.7 跳转地址与浏览器回跳

Checkout 的 success_url 和 cancel_url 来自后端受控配置的 OrionAI 前端基址，不接受任意客户端 URL，防止开放重定向。success_url 中仅携带不可用于付款授权的订单标识/Stripe 占位符；回跳后页面查询本地订单。前端显示处理中直到订单 API 返回 paid。cancel_url 回来不代表订单失败。

## 8. 前后端流程与失败处理

### 8.1 正常流程

1. 前端打开会员中心，同时请求套餐列表和本人会员期限。
2. 用户选择档位，前端生成 UUID request_id，调用创建订单接口。
3. Membership Service 校验套餐状态并写入订单及 amount/duration_days 快照。
4. 前端使用 order_id 调用 Payment API 创建 Checkout Session。
5. Payment Service 读取订单支付上下文，经 Stripe Gateway 创建 Checkout Session，将 Session ID 回写订单，返回 URL。
6. 用户在 Stripe Checkout 沙盒完成付款。
7. Stripe 调用 Webhook。Payment Gateway 校验原始请求签名并转换事件。
8. Payment Service 核验订单和 Session 对应关系后调用 Membership Service。后者锁订单和用户，校验金额/币种/支付状态，计算期限并在一个数据库事务写 paid 及 memberships。
9. 浏览器回跳后轮询订单状态和会员期限；后端确认 paid 后页面展示成功及当前/排期待生效期限。

### 8.2 失败与恢复策略

| 场景 | 服务端处理 | 用户可见结果/恢复 |
|---|---|---|
| 用户重复点击创建订单 | request_id 唯一约束并返回同一订单 | 继续同一个支付流程 |
| 同幂等键改选套餐 | 返回 409，不修改原订单 | 前端生成新 request_id 再下单 |
| Stripe 创建 Session 失败 | 订单保留 pending；客户端可用原订单重试；网络调用不包在数据库事务中 | 显示暂不可用，可重试 |
| Stripe 已创建、响应或本地保存 Session ID 时网络中断 | 用订单级稳定 Stripe Idempotency-Key 恢复；如本地已有 ID 则 Retrieve；记录受控错误以便运维排查 | 用户重试后取回原 Session，不应创建多个会话 |
| 用户关闭支付页/取消返回 | 未收到支付确认时订单仍 pending | 页面显示处理中；Checkout 过期后创建新订单 |
| Checkout Session 过期 | 验证 Session ID 后将未支付订单置 expired；不再复用订单 | 创建新订单并重新支付 |
| Webhook 签名无效或 livemode=true | 拒绝处理并告警/记录受控原因 | 不改变订单和会员 |
| 金额、币种、metadata、订单用户或 Session ID 不匹配 | 不发放期限；记录关联订单/事件 ID及错误类别 | 订单不显示成功，触发运维调查 |
| Webhook 重复或乱序 | 锁定订单；paid 不降级；memberships.order_id 唯一 | 返回可重试安全的 2xx；期限仅一条 |
| 数据库事务失败 | 整笔回滚；为非 2xx 让 Stripe 重试；重试时仍走幂等入账 | 前端保持处理中 |
| 同用户多笔支付并发成功 | 锁 users 行后重新查询最大 expires_at；排斥约束拒绝任何重叠期限 | 两段期限按事务先后串行排期 |
| 其他用户猜测 order_id | 所有本人查询和 Checkout 创建均按可信 user_id 过滤 | 返回统一 404 |

注意：Stripe Session 创建与 PostgreSQL 事务不是原子操作。订单级 Stripe 幂等键、持久化 session_id、短时 Session 有效期和可重试 Webhook 用于覆盖跨系统故障；不声称实现跨系统分布式事务。

## 11. 测试与验收标准

| 类别 | 必须验证的行为 |
|---|---|
| 套餐 | 默认种入三档金额和期限；停用套餐不返回且不能新下单；已有 pending 订单快照仍可支付 |
| 订单 | 客户端不能指定用户、金额、币种或天数；同用户同 request_id 幂等；相同 request_id 换套餐返回 409 |
| Checkout | 仅订单所有者能创建/恢复；金额来自订单 Decimal 快照；CNY 转 Stripe 最小货币单位正确；Checkout URL 不入库 |
| Webhook | 无效签名、live mode、错误 Session、metadata、金额、币种、未支付状态均不授予会员 |
| 幂等 | 同一成功 Webhook 多次投递只产生一条 memberships；paid 不被 failed/expired 覆盖 |
| 期限 | 首次从确认时间开始；后续购买从最大 expires_at 顺延；不同档位同样顺延；结束等于开始加 duration_days |
| 并发 | 同用户并发支付不产生重叠期限、不丢失时长；排斥约束作为数据库保护 |
| 权限 | 未登录 401、访客不能下单/读个人会员、其他用户订单统一 404 |
| 回跳 | 前端仅以本地订单 API 的状态显示成功；取消和跳转不构成付款确认 |
| 回归 | 不改现有 users 表和 AI 功能权限；现有 API、登录和导航保持原行为 |
| 迁移 | PostgreSQL 新库 upgrade 创建三表/约束/种子；upgrade 可重复验证；downgrade 不误删共享扩展 |

计划中的测试类型包括单元测试、API/数据库集成测试、PostgreSQL 并发测试、迁移测试和 Stripe CLI 沙盒验收。实际实现后应执行项目要求的静态检查与自动化测试，并如实记录结果。

## 13. 安全、运维与可观测性

- Stripe secret、webhook secret 用 SecretStr/环境变量管理；仓库只记录空值示例，禁止提交真实密钥。
- 只启用 Stripe 测试环境配置；所有支付事件要求 livemode=false。生产收款属于后续独立发布决策。
- Webhook 必须验原始请求体签名；设定合理 body size 上限；不要在日志写入原始载荷、支付凭证或秘密。
- 订单创建、Checkout 创建和 Webhook 处理日志记录内部订单 ID、Stripe Session/Event ID、状态转换和受控错误类别。
- Stripe Checkout 成功、失败或延迟都以本地订单为准；对失败事务返回可重试错误，避免“已收款但本地无会员”被静默吞掉。
- 配置 Checkout 回跳 URL 白名单；不接受任意客户端 redirect URL。
- 用户 API 必须从 RegisteredUser 获取 user_id；所有订单/期限 Repository 查询显式按 user_id 过滤。
- btree_gist 扩展需要在 PostgreSQL 环境可用；部署前确认数据库角色有创建扩展权限，若托管环境不允许，需在实施前确定由 DBA 预置或采用受支持的迁移方案。

## 14. 风险、假设与待评审点

| 项目 | 当前方案 |
|---|---|
| Stripe Session 与数据库不能原子提交 | 订单级 Stripe Idempotency-Key + 本地 stripe_session_id + Retry/Retrieve + Session 最大 24 小时有效期；不承诺分布式事务 |
| 方案要求最小表结构，但需处理支付可靠关联 | 保留唯一 stripe_session_id；不保存可通过 Retrieve 获取的 checkout_url |
| 同一用户并发付款 | 锁 users 行串行计算 + PostgreSQL 排斥约束；需要验证 btree_gist 运维条件 |
| 套餐种子和后台维护并存 | 以唯一 name 做冲突键，迁移重复执行不覆盖已有启用状态；价格调整通过新迁移/明确数据维护 |
| 订单历史的套餐名展示 | 不保存冗余 plan_name_snapshot，关联当前 plan.name；禁止物理删除；如需精确历史名称快照，再由业务明确决定是否加字段 |
| async payment 方法 | 首期限定 Stripe Checkout 的即时支付方式，避免延迟支付在过期/失败事件后到账造成状态歧义；如需异步支付方式，应先扩展事件状态规则并复核过期处理 |
| 表字段类型 | user_id 和所有主键延续 Snowflake BIGINT；API 用十进制字符串承载 ID；金额用 Decimal/NUMERIC |
| 回滚 | downgrade 会删除新增业务表；任何真实交易后不应直接降级，应先备份并按运营方案处理交易数据 |

当前没有待用户补充的首期业务决策。实现前需要在代码评审中确认 btree_gist 可用、Stripe 允许的支付方式以及套餐名称作为稳定自然键的运维约定。
