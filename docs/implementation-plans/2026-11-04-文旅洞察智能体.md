# 文旅洞察智能体实现方案

> 日期：2026-11-04（Asia/Shanghai）  
> 状态：已按方案实施；自动化测试、静态检查和一次性数据库迁移验证已执行

## 1. 实现后的效果与完整使用流程

1. 已登录且具备现有技能使用资格的用户在技能市场添加并打开“文旅洞察”，进入专属页面；页面内保留“数据管理、智能分析、分析结果”三个标签，不增加全局导航。
2. 首次在“数据管理”上传 `.xlsx` 评分表。系统读取 `T6-评分大表`，展示导入、跳过和错误数量；没有有效规则时，分析按钮和对话发送均提示先导入规则。用户可选上传 UGC `.csv`，指定本次最多导入条数，查看有效评论列表。
3. 在“智能分析”中，用户可以勾选一条或多条已导入评论发起分析，也可以直接在页面对话框输入游客评价并发送。两种入口使用同一套匹配流程。有效的手动输入保存为当前用户的评论，出现在评论列表和历史结果中；对话消息另由现有会话系统保存。
4. 智能体先判别本轮内容是否属于文旅评论、景区服务体验及评分规则匹配业务。无关提问只回复业务范围和示例输入，不检索规则、不创建评论或匹配结果。相关输入被拆成独立评价事实，每个事实检索少量候选评分子项，再由模型结合评分口径、简要说明和数据源判断。匹配到的规则 ID、原文证据、理由和状态经过程序校验后保存。
5. 对话框显示简短结论及进入结果页的入口；“分析结果”按评论展示大项 → 分项 → 指标 → 子项、Excel 原文口径、证据及依据。无法确认时明确显示“待核验”或“未匹配”，不计算分值。刷新后仍可查看评论和结果。
6. 重新上传评分表时先预解析和校验；只有新表可用才在同一数据库事务中清除该用户旧匹配结果、替换旧规则，并启用新规则。评论和对话记录保留，评论分析状态变为未分析，用户可全部重新分析。页面在确认覆盖前明确提示这一影响；解析失败时原规则和旧结果保持原状。

## 2. 需求、范围与决策

依据外部《OrionAI-文旅洞察智能体需求文档》V1.1 与本轮补充：评分规则 Excel、UGC CSV、评论分页及批量选择、自由文本对话、真实规则匹配、证据解释、结果保存、业务范围约束、按用户隔离。用户已确认：手动输入保存到评论库；规则重传清空旧结果，按新规则重做。

本期不做分数计算、全量自动批处理、人工审批、景区报告、向量数据库或多智能体。批量上限建议 10 条、CSV 默认导入上限 50 条、单次最大 100 条作为非阻塞配置假设，实施时集中放入 `constants.py`，避免散落魔法值。无关内容仅进入既有会话消息历史，不进入业务评论库。空文本和超长文本按既有输入契约拒绝。

## 4. 架构与数据流

`tourism_insight` 作为 `backend/app/modules/` 下的业务模块，负责文件解析、评论与规则、匹配持久化和查询；`backend/app/modules/agents/tourism_insight/` 只负责 LangGraph、提示词、节点、工具和运行时。Router 只验参/组织响应，Service 处理事务和规则，Repository 只访问数据。Agent 不直接依赖 FastAPI 或 ORM；通过创建 Runtime 时注入的业务读取/写入接口获取可信 `user_id`（来自会话配置，而非模型工具参数）。

### 图节点及工具设计

```text
START → input_node(复用) → scope_node(新增)
  ├─ 无关 → output_node(复用) → END
  └─ 相关 → analyze_node(新增，事实提取、规则检索、匹配及初步校验)
            → persist_reply_node(新增，最终校验、保存及答复)
            → output_node(复用) → END
```

| 节点/工具 | 输入与职责 | 复用判断 |
|---|---|---|
| `input_node` / `output_node` | 校验用户文本、抽取最终回答 | 直接复用 `app.agent.nodes`。批量评论每条以原评论文本进入相同图。 |
| `scope_node` | 模型结构化判别 `in_scope`；无关请求直接写固定业务引导消息。只判断本轮输入。 | 新增；通用模型节点没有业务分类职责。 |
| `analyze_node` + `tools/search_rules.py` | 从原文提取事实；按可信用户身份检索少量真实候选；模型结构化匹配；在节点内校验候选 ID、证据原文和状态，只把已校验结果写入 State。 | 新增；现有工具无评分规则查询，拆成多个图节点不会增加实际能力。 |
| `persist_reply_node` | 调用业务 Service 再核实规则仍属于当前用户，原子保存手动评论/匹配结果或替换已有评论结果，写入简短答复消息。 | 新增；保存是确定性业务操作，不暴露给模型作为工具。 |

`tools/` 仅存放需要的 `search_rules.py`；该工具由 `analyze_node` 以可信用户上下文调用，不让模型指定用户 ID。持久化由业务 Service 执行，无需另造保存工具。`prompts/system.md` 保存业务边界和不能编造规则的要求；`prompts/analysis.md` 约束事实抽取与匹配。结构化 Pydantic 输出放在 Agent 的 `schemas.py`。

### State（仅本轮必要字段）

`tourism_insight/state.py` 定义专属 `TourismInsightState`，包含自己的 `messages`、`answer`、通用输出节点使用的 `question_round_count`，以及一个业务上下文 `analysis_context`（只保存 `in_scope` 与 `validated_matches`）。这样图与 State 都由新智能体单独定义，同时沿用输入/输出节点契约。原文从本轮 `HumanMessage` 读取；批量的 `source_comment_id` 与可信 `user_id` 从运行配置取得；事实和候选只在 `analyze_node` 内使用；规则与结果从数据库读取。每轮 `scope_node` 重置 `validated_matches`，防止 Checkpointer 沿用上轮结果。

### 持久化和覆盖策略

采用三张业务表，不额外建导入批次表：`scoring_rules`、`ugc_comments`、`comment_matches`。规则重传时清空当前用户的 `comment_matches` 和 `scoring_rules`，再写新规则；评论保留。这样无需规则版本表，且符合用户明确选择的“旧结果清空”。文件内去重基于规范化后的指标编号、子项序号及名称；新导入作为当前用户规则全集，不叠加旧规则。分析状态由是否存在当前匹配记录及最近分析时间推导，避免单独状态字段与结果漂移；“未匹配”也保留一条分析记录（`rule_id` 为空），以便复查和计数。

## 5. 接口影响清单

所有新业务接口位于 `/api/tourism-insight`，沿用现有登录用户依赖、来源校验和技能/会员准入。响应 ID 一律为十进制字符串。业务错误使用模块异常处理器映射为明确 4xx/5xx。

| 方法与路径 | 操作/契约 | 复用与理由 |
|---|---|---|
| `POST /api/conversations` | 保持不变；`skill_code=tourism_insight` 创建会话 | 自由输入需要现有会话消息历史。 |
| `POST /api/conversations/{id}/messages`、`.../stream` | 保持不变；普通文本进入新 Runtime，返回文本结论 | 复用既有会话与 SSE 契约，不新增聊天 API。 |
| `GET /api/conversations/{id}/messages` | 保持不变；恢复对话 | 复用既有接口。 |
| `POST /api/tourism-insight/rules/import` | 新增；multipart `.xlsx`，返回导入/跳过/失败计数和错误摘要；覆盖前需请求显式 `replace=true` | 现有 API 无规则导入。成功原子清空旧结果；无效文件不清空。 |
| `POST /api/tourism-insight/comments/import` | 新增；multipart `.csv` + `limit`，返回三类计数和错误摘要 | 现有 API 无评论导入。 |
| `GET /api/tourism-insight/summary` | 新增；规则数、评论数、已分析数、规则就绪状态 | 数据管理/分析页需要。 |
| `GET /api/tourism-insight/comments?limit=&offset=` | 新增；当前用户分页评论、来源、时间、状态 | 现有消息接口不等于评论库。 |
| `POST /api/tourism-insight/analyses` | 新增；`comment_ids: string[]`（1～10）；逐条执行同一分析图，返回每条成功/失败及结果 ID | 批量选择不能通过自由文本接口安全传可信评论 ID。 |
| `GET /api/tourism-insight/results?limit=&offset=` | 新增；按评论分页返回持久结果，服务端按真实规则记录拼接层级与口径 | 现有消息接口不承载结构化结果。 |

## 6. 数据库影响清单

已核查现有 `conversations/messages/skills/user_skills` 模型和迁移；它们没有评分规则、评论或匹配关系字段。新表字段为满足原文追溯、用户隔离和结果复查的最小集合。迁移拟新增 `backend/migrations/versions/0019_tourism_insight.py`；无历史回填。

| 表与字段 | 操作 | 目的与约束 |
|---|---|---|
| `skills` 的一条 `code=tourism_insight` 记录 | 新增数据，表结构不变 | 技能市场/会话入口；由现有 ensure 技能模式写入。 |
| `conversations`、`messages` | 不变 | 复用会话和消息持久化。 |
| `scoring_rules.id`, `user_id` | 新增 | Snowflake ID、用户归属；`user_id` 外键及索引。 |
| `scoring_rules.major_item`, `minor_item`, `indicator_code`, `indicator_name`, `subitem_number`, `subitem_name` | 新增 | 完整指标层级与规则去重键。 |
| `scoring_rules.scoring_criterion`, `description`, `data_source_detail` | 新增 | 保留 Excel 原文、解释和证据来源。 |
| `ugc_comments.id`, `user_id`, `source_type`, `original_id` | 新增 | 内部 ID、归属、`csv/manual` 来源及原 CSV ID；手动输入原始 ID 为空。 |
| `ugc_comments.nickname`, `ugc_type`, `platform`, `title`, `content`, `published_at` | 新增 | 列表、证据、原始评论信息；手动输入只要求 `content`。 |
| `comment_matches.id`, `user_id`, `comment_id`, `rule_id` | 新增 | 当前用户的评论与规则关联；未匹配时 `rule_id` 可为空。 |
| `comment_matches.evidence`, `reason`, `status`, `created_at` | 新增 | 可解释结果及 `matched/review/unmatched` 状态；未匹配不强制理由。 |

迁移创建用户/评论/规则外键、`(user_id, indicator_code, subitem_number, subitem_name)` 规则唯一约束、评论分页索引和匹配查询索引。CSV 重复记录按 `(user_id, platform, original_id)` 中非空原始 ID 去重；手动评论不按文本去重，允许用户再次发送同文。规则重传和结果清空在同一事务中进行；数据库失败回滚。回滚迁移会删除三张新表，部署时应先备份业务数据。

## 9. 风险和运行考虑

- 评分表实际列头/合并单元格、CSV 编码可能与需求样例不同；解析器按确认的列名给出逐行错误，实施前用真实样本验证，不为了未知格式添加大量兼容分支。
- 规则重传与分析并发时，通过事务锁定当前用户规则集并在保存时复核规则仍存在，避免写入已删除规则；重传确认框说明旧结果会删除。
- 输入、CSV 行数、文件大小、批量条数和候选数量设置明确上限；模型只接收当前少量候选，不发送整份评分表。原评论可能含个人信息，日志只记 ID/数量/错误类型，不记录原文。
- 页面继续使用现有会员准入和登录身份；业务接口服务层所有查询及写入都以可信 `user_id` 限定。无关回复、候选 ID 校验均由程序边界保证，提示词仅作辅助。

## 10. 完成定义

用户可通过导入评论或手动对话完成文旅规则匹配，查看并复查结构化结果；无关请求被引导；规则重传按已确认策略清空旧匹配且失败不破坏原数据。全部文件职责、API/数据变更与上表一致，测试和静态检查结果在实施时记录。
