# 数字人直接创建提醒实现方案

> 历史设计记录：本文反映编写时的需求或方案，可能与当前实现不同；当前行为请查阅 [README](../../README.md)、[架构概览](../architecture/overview.md)及源码。

> 日期：2026-11-06（北京时间）  
> 状态：待审阅

## 1. 目标与范围

用户在数字人会话中明确要求创建提醒时，数字人从原话提取参数，缺项时使用现有 `ask_user_questions` 题卡继续收集，参数齐全后调用一个新的 `create_reminder` 工具。工具复用 `ReminderCreateRequest` 和 `ReminderService.create`，创建结果返回模型，再由模型回复用户。按本轮已讨论的方案，参数齐全后直接创建，不新增确认题卡、图节点、HTTP 接口或提醒插入逻辑。

只支持现有单次、每天、每周、每月四类提醒；不扩展提醒规则、投递方式或前端页面。

会话中的数字人运行与提醒 REST API 使用不同入口。新工具调用同进程 Service，不发内部 HTTP 请求，也不直接执行 SQL。提醒 API 的 `POST /v1/reminders` 所用会员准入依赖不会自动作用于工具；工具执行前须复用 `MembershipAccessService.require_member` 或等效的现有业务服务，并从可信运行上下文取得用户，拒绝访客。

## 3. 参数与交互规则

| 类型 | 必填计划字段 | 可选字段 | 互斥字段 |
|---|---|---|---|
| `once` | `date`, `local_time`, `timezone` | 无 | `start_date`, `end_date` |
| `daily` | `start_date`, `local_time`, `timezone` | `end_date` | `date` |
| `weekly` | `start_date`, `local_time`, `timezone` | `end_date` | `date` |
| `monthly` | `start_date`, `local_time`, `timezone` | `end_date` | `date` |

每类还需要 `title` 和 `content`。周几及每月几号由 `start_date` 推导。提示词应要求模型仅对用户明确提出的创建请求调用工具；缺少日期、时间、重复方式、提醒内容或存在歧义时先提问。相对日期先调用 `get_current_date`。模型需将“每周一”转为**未来的**某个星期一作为 `start_date`；`ReminderService` 会拒绝首次执行时间不晚于当前时刻的参数。

非阻塞假设：用户没有指定时区时使用 `Asia/Shanghai`，并在创建结果中明确展示；明确指定其他时区时采用有效 IANA 时区。该默认与当前北京时间日期工具一致。标题可由用户表达的提醒事项简要生成，正文保留完整事项；事项本身不清楚时应追问。

执行顺序：用户消息 → 模型提取已知字段 → 缺项/歧义时题卡提问并等待 → 参数齐全时调用 `create_reminder` → 工具校验字段和权限 → `ReminderService.create` → 依据返回的 ID、计划时间和类型回复。校验或创建失败时不得声称成功；可纠正的时间/字段错误提示模型继续询问，基础设施失败向用户说明创建未完成。

## 5. 接口与数据库影响

| 接口 | 操作 | 契约与兼容性 |
|---|---|---|
| `POST /v1/reminders`（`backend/app/modules/reminders/router.py`） | 保持不变 | 仍调用 `ReminderService.create`；新工具在进程内复用该 Service。 |
| `POST /conversations/{conversation_id}/runs/messages`、`POST /conversations/{conversation_id}/runs/answers`（`backend/app/modules/conversations/router/router.py`） | 保持不变 | 沿用会话及题卡协议；新增的仅是数字人可执行能力。 |
| 数字人内部工具 `create_reminder` | 新增 | 入参对应 `ReminderCreateRequest` 的业务字段；输出创建结果或明确失败信息；不构成公开 HTTP API。 |

**无数据库表、字段、索引或迁移变更。** 已核查 `backend/app/modules/reminders/models.py` 的 `reminders` 模型和 `ReminderService.create`；现有字段足以保存四类提醒。现有调度器继续读取相同提醒记录。

## 6. 分步实施与验收

1. **工具与业务复用。** 新增 `tools/reminder.py`，使用严格输入模型、可信 `user_id` 查用户及会员资格、请求模型校验，并用独立且及时关闭的数据库会话调用 `ReminderService.create`。验收：参数不能指定归属用户；无会员或访客不创建；合法请求生成当前用户的一条提醒；无效时间及数据库错误不返回“已创建”。测试：`test_digital_human_reminder_tool.py`、现有提醒 Service 测试。
2. **数字人接入。** 修改 `graph.py`、`capabilities.py`，注册工具并描述类型映射、缺项询问和相对日期规则。验收：工具在注册列表及能力提示中出现；缺项时题卡等待，回答后可继续；有效创建结果返回模型。测试：`test_digital_human_agent.py`。
3. **清理旧方案与回归。** 将旧未跟踪确认测试替换/删除，检查无需再保留的草稿确认假设。验收：提醒相关测试可收集；现有邮件题卡、数字人普通工具及提醒 CRUD 测试通过。测试：相关 `pytest`，并执行适用的 Ruff 静态检查。

## 7. 风险与验证重点

- **模型提取误差：** 通过题卡补齐歧义字段、日期工具确定相对日期、请求模型和 Service 二次校验；测试覆盖四类提醒及过去时间。
- **重复创建：** 现有会话消息幂等键只保护部分入口，不能单独证明“数据库已提交但工具结果丢失后重试”不会重复创建。本方案不宣称严格恰好一次；实施时应测试同一工具调用重复执行的行为，并优先复用现有会话 run ID 做调用级去重。如需跨崩溃的严格恰好一次，需另行评估数据库唯一约束及迁移，不能仅凭 Redis 声称保证。
- **权限：** 会话入口的会员校验不能替代工具内部检查；以当前用户 ID 读取真实用户状态，不信任模型参数。
- **运行资源：** 工具由异步图调用，数据库和 Redis 的同步操作应沿用项目工具执行方式，并确保会话关闭；不记录提醒正文、邮箱或凭据。

完成条件：四类提醒能通过数字人收集参数并创建；缺项、权限不足和创建失败均有正确行为；不增加图节点、公开 API 或提醒表结构；旧确认测试不再阻断测试收集；验证结果在实施时如实记录。
