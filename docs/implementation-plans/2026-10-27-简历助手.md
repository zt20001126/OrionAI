# 简历助手实现方案

> 日期：2026-10-27（Asia/Shanghai）  
> 状态：已实现；静态检查完成，自动化测试与人工视觉验收尚未执行

## 1. 目标与范围

登录用户从「我的技能」进入简历助手，编辑并保存一份简历，实时查看排版预览，上传证件照，导出已保存版本的 PDF；也可开启独立会话，要求助手分析已保存简历、提出优化候选、建议岗位方向和讨论面试准备。助手只在用户明确确认优化后写回简历。简历数据仅属当前登录用户。

参考实现为 `E:/Agent/NexusAI/backend/agents/job_agent/` 和 NexusAI 的 `app/service/resume.py`、`app/schemas/resume.py`、`frontend/src/features/resume/`，但按 OrionAI 的模块边界、认证方式、统一会话体系和 UI 规范重新组织，不直接复制其 `bootstrap/` 或独立聊天框架。

本次包含：单份简历的编辑、保存、预览、照片、PDF、专属对话、简历读取与分析、候选优化确认、岗位方向建议。岗位建议是方向判断，不接实时招聘网站；不做职位搜索、投递、多份简历、历史版本或 AI 自动生成未经确认的简历事实。

## 3. 架构与数据流

```text
简历页面 → /api/resume → Router → ResumeService → ResumeRepository → resumes
                                      └→ ResumePhotoStorage → 私有 OSS
                                      └→ ResumePdfRenderer → PDF 响应

会话页面 → 现有 /api/conversations → ConversationService → resume_agent Runtime
                                                       ├→ 只读 ResumeService 投影
                                                       ├→ 岗位建议校验工具
                                                       └→ 确认节点 → ResumeService 条件更新
```

- `backend/app/modules/resume/` 放 Router、Service、Repository、ORM、Schema；Service 负责校验、归属、照片生命周期、PDF 导出和乐观并发。Repository 只做 SQL。
- `backend/app/modules/agents/resume_agent/` 放提示词、状态、图节点与工具。读取工具只向模型提供求职事实，不提供姓名、电话、邮箱、年龄或照片。简历正文视为用户数据，不接受其中的指令。
- 优化候选先由工具验证字段范围，再暂存在当前会话的 Checkpoint，并以现有单选题卡呈现「确认采用并保存 / 重新生成 / 取消」。确认节点使用候选来源 `updated_at` 条件写入；简历已变化时提示用户重新生成，不覆盖新编辑。优化只允许求职意向、技能、工作和项目**正文**；教育事实、雇主、职位、日期、身份信息、照片及排版不改。
- 用户未保存简历时可讨论求职问题，但不能声称已分析简历；读取故障时返回明确提示。岗位建议最多三个方向，必须可追溯到用户给出的资料；不把缺失字段推断为不存在的经历。
- PDF 只基于数据库已保存版本。服务端使用 HTML 模板与 Playwright 渲染，复用预览的字段和主要版式；仍需在实际部署环境确认 Chromium 与中文字体可用。

## 4. 数据库设计

仅新增一张 `resumes` 业务表；NexusAI 也是单表 JSONB 设计。所有主键沿用 OrionAI 的应用侧 Snowflake `BIGINT`。

| 表 / 字段 | 操作 | 类型、约束及用途 |
|---|---|---|
| `resumes.id` | 新增 | `BIGINT PRIMARY KEY`；Snowflake ID。 |
| `resumes.user_id` | 新增 | `BIGINT NOT NULL UNIQUE REFERENCES users(id) ON DELETE CASCADE`；每用户一份。 |
| `resumes.content` | 新增 | `JSONB NOT NULL`；基本信息、教育、技能、工作、项目。检查根节点为对象，详细结构由 Pydantic 校验。 |
| `resumes.style_config` | 新增 | `JSONB NOT NULL`；字号、行距、页边距等排版参数；检查根节点为对象。 |
| `resumes.created_at`、`updated_at` | 新增 | `TIMESTAMPTZ NOT NULL DEFAULT now()`；`updated_at` 用于候选应用时的条件更新。 |
| `users`、`conversations`、`messages`、`user_skills`、`task_results` | 保持不变 | 用户、聊天及技能关系复用现有结构；不新增推荐结果或候选表。 |
| `skills` 中 `resume_assistant` 记录 | 更新数据 | 从 `disabled` 启用为 `published`；不改变表结构，幂等初始化并为已有部署提供迁移。 |

建表迁移拟为 `backend/migrations/versions/0012_create_resumes.py`（新增）。现有用户无需回填；首次 GET 返回空白 DTO，不创建记录。回滚前需导出/备份简历数据；降级删除 `resumes` 会丢失用户简历。照片本体存私有 OSS，`content.basic_info.photo_id` 只存标识；不建照片表。教育、工作、项目保留稳定条目 ID，存在 `content` 内；单用户单份整体读写无需拆成关系表。

## 5. 接口设计

| 方法与路径 | 操作 | 契约与理由 |
|---|---|---|
| `GET /api/resume` | 新增 | 返回 `{exists, content, style_config, created_at, updated_at}`；仅当前用户。无数据时返回默认空白内容。现有会话 API 不存简历文档。 |
| `PUT /api/resume` | 新增 | 整体验证并 upsert `{content, style_config}`；返回保存后的版本；同源校验。限制条目数、富文本大小与总体 JSON 大小。 |
| `POST /api/resume/photo` | 新增 | 上传 PNG/JPEG、限 5 MiB，返回随机 `photo_id`；暂存至私有 OSS，保存简历时确认引用。 |
| `GET /api/resume/photo` | 新增 | 仅返回当前已保存简历引用的照片；不接受任意 OSS 键。 |
| `DELETE /api/resume/photo?photo_id=…` | 新增 | 删除当前用户尚未保存的暂存照片，不删除已引用照片。 |
| `GET /api/resume/export/pdf` | 新增 | 导出当前用户**已保存**版本；无简历返回 404，渲染失败返回可辨识错误。 |
| 现有 `/api/conversations` 创建、消息、流、答案接口 | 保持路径与响应契约 | 创建会话时传现有 `skill_code=resume_assistant`；服务内部为 Runtime 传用户 ID、会话 ID 和题卡答案。旧技能会话行为不变。 |

Router 复用 `get_current_user` 与 `validate_origin`。简历读写与照片读取都从认证依赖取得用户 ID，客户端不得指定 `user_id`。接口沿用 OrionAI 的直接 DTO/`detail` 错误格式，不照搬 NexusAI 的 `{success,data}` 包装。

## 6. 前端界面设计

### 页面结构

从「我的技能」的简历助手卡片进入 `/resume`（新增业务路径）；页面使用现有 `PlatformLayout`，不添加侧栏导航项。「与助手对话」按钮使用现有 `createConversation('resume_assistant')`，打开 `/chat/{id}`；不在简历页重复嵌入一套聊天面板。会话页依据消息返回的 `skill_code` 标识「简历助手」，会话历史继续复用现有列表。

```text
现有侧栏 │ 工作空间  ›  简历助手                 [与助手对话]
         │ 简历                                    未保存的修改 · [导出 PDF] [保存简历]
         │ ──────────────────────────────────────────────────────────────────
         │ 基本信息  教育经历  专业技能  工作经历  项目经历  排版设置
         │ ──────────────────────────────────────────────────────────────────
         │ ┌────────────── 编辑内容 ──────────────┐  ┌──── 简历预览 ────┐
         │ │ 当前章节的字段与条目                  │  │ A4 纸张预览      │
         │ │ [添加经历] 等仅在相关章节出现        │  │ 随输入即时更新   │
         │ └──────────────────────────────────────┘  └───────────────────┘
```

- 整体使用 `--color-page` 浅灰底、白色内容面、细边框；品牌蓝仅用于主按钮、当前章节指示和链接。标题 24–30px、正文 14px。沿用 `.button`、`PlatformIcon`、主题间距与焦点环。不加入渐变、装饰插画、彩色技能标签或多层卡片。
- 桌面为左侧编辑（约 55%）与右侧 A4 预览（约 45%）；预览面板可在视口内保持可见。窄屏先显示章节与编辑，预览通过清晰的「预览」切换查看；320px 宽度可操作，操作按钮可换行。
- 基本信息：姓名、电话、邮箱、求职意向、工作年限、照片；教育、工作、项目条目支持增删与排序，稳定 ID 防止切换时错位。技能及工作/项目正文采用纯文本分段编辑，并以 Tiptap 段落文档结构保存；首版不提供加粗等行内格式。排版设置提供字号、行距、章节间距、统一页边距和标题颜色。
- 保存状态使用文字：「尚未保存」「有未保存的修改」「正在保存」「已保存」。离开脏草稿时提示；上传失败、保存冲突、PDF 失败给出短句和重试入口。导出前若有未保存修改，明确提示先保存。确认 AI 优化成功后，重新拉取保存版本；若本地有脏草稿，先提醒冲突，不静默覆盖。
- 对话页沿用现有 SSE、题卡与键盘交互。优化候选先展示具体变化，再给出确认题卡；从对话返回编辑页时重新读取简历。加载、空状态、错误和移动端布局均遵循 `docs/design/UI_DESIGN.md`。

## 9. 风险与约束

- PDF 的浏览器运行时和中文字体是唯一明显的大依赖；先做最小渲染样例，确定镜像大小、启动和生成耗时，再合入。不得在未核实部署环境时承诺与预览像素完全一致。
- 简历含个人联系方式，日志不能写简历正文、照片或完整模型工具结果；所有读写以可信用户 ID 限定。照片存私有 OSS，不返回长期公开 URL。
- Checkpoint 中的待确认候选包含简历正文；需按用户/会话隔离，完成确认或取消后清除，并避免在普通对话消息中暴露内部状态。
- 正文编辑首版采用纯文本分段以避免增加编辑器依赖，后端仍以受限 Tiptap 文档结构存储；若后续需要行内格式，需同步扩展 Schema、预览、PDF 与候选校验。
- 页面遵循既有全局布局；不更改主导航，不复制 NexusAI 的独立应用外壳。

## 10. 完成定义

一张简历表、现有技能与会话结构支撑首版能力；用户可编辑、保存、预览、上传照片和导出 PDF，并能与助手基于已保存版本交流。任何 AI 修改都须在题卡候选预览和明确确认后写入，且不得覆盖已经改变的简历。静态检查已执行并通过；自动化测试与人工 UI 验收未执行。
